# Telegram — Studio 19.25

Уведомления адресованы только подключённым сотрудникам. Клиентская бронь подтверждается после SQLite COMMIT, независимо от доступности Telegram. Интерфейс, публичный API, HTTPS и VPN не меняются. Уведомления по умолчанию **выключены**.

## Устройство

Миграция `0003_telegram_notifications.sql` добавляет получателей, хешированные приглашения, позицию long polling, lease обработчика и transactional outbox. Миграции 0001/0002 не меняются. Триггер при новой подтверждённой брони создаёт задания активным подключённым получателям в той же транзакции; уникальность `(booking_id, recipient_id)` и существующий стабильный ID брони исключают повторные задания при повторе POST. Старые брони не рассылаются задним числом.

Один лёгкий обработчик работает **в существующем процессе Next.js**, запускается через Node instrumentation в SERVER при `STUDIO_TELEGRAM_WORKER=1`. `dev:server`/`start:server` и управляемый systemd unit задают этот флаг; сборки отключают его. Ни отдельной службы, ни контейнера, ни публичного Telegram endpoint нет. Отсутствие конфигурации бота не мешает бронированиям. Для прямого `next start` вне установщика флаг нужно указать явно. DEMO принудительно отключает обработчик.

SQLite lease на 60 секунд с heartbeat каждые 10 секунд допускает одного обработчика на базе. После штатной остановки lease освобождается, после аварии — истекает. Отправка и long polling независимы: ожидание updates не задерживает очередь. Update offset и использование приглашения фиксируются атомарно, поэтому повтор Telegram update не привязывает аккаунт второй раз. Telegram хранит необработанные updates ограниченное время (обычно не более 24 часов); после длительного простоя неиспользованное приглашение нужно обновить.

Отправки начинаются не чаще раза в 1,1 секунды для всего бота; временные ошибки повторяются с растущей задержкой до 15 минут, `429 retry_after` останавливает весь sender на указанный срок. Каждое задание имеет неизменный deadline `created_at + 24 часа`. Начатый HTTP-запрос ограничен 8 секундами и остатком этого окна. Постоянные ошибки (например, блокировка бота получателем) завершают задание. Ошибка авторизации видна как технический код; не повторяется бесконечно для одного задания. После восстановления токена не создаются новые задания взамен окончательно завершённых.

При глобальном выключении новые задания сохраняются, отправки старых и новых приостановлены. После включения уходят только ещё актуальные. Просроченные помечаются `failed / DELIVERY_EXPIRED`; при остановленном обработчике это происходит при его следующем запуске либо запросе административного статуса. Отключение/отзыв сотрудника сразу отменяет его ожидающие задания; повторное включение не оживляет отменённые. Перепривязка требует нового приглашения.

Проверка активности/глобального флага и начало сетевой попытки сериализованы короткой SQLite IMMEDIATE-транзакцией. Ожидание HTTP **не держит** writer lock. Если отключение зафиксировано первым, отправка не начинается. Уже начатую сетевую попытку нельзя гарантированно отозвать; полученное ранее сообщение удалить из Telegram сотрудника нельзя. Потеря ответа или падение после принятия сообщения Telegram может привести к повторной доставке. Bot API не предоставляет exactly-once: защита от повторных заданий и fencing результата уменьшают дубли, но не устраняют эту неопределённость.

## Создание бота и защищённая конфигурация

Действия ниже выполняются владельцем **после согласованного обновления**, не этим PR.

1. В официальном `@BotFather` выполнить `/newbot`, выбрать название и username. Использовать одного бота. Его можно передать другому владельцу через BotFather. Не назначать боту права управления бронями; такие команды вообще не реализованы.
2. Сохранить выданный токен в менеджере паролей. Не отправлять его в чат разработки, GitHub issue, Actions input, командную строку, скриншот или журнал.
3. В защищённом редакторе создать `<каталог SQLite>/settings/telegram-bot.json` с JSON следующей структуры, заменив значение **в редакторе**, без `echo TOKEN` и без shell history:

   ```json
   {"version": 1, "token": "ВСТАВИТЬ_ТОКЕН_ТОЛЬКО_В_ЗАЩИЩЁННЫЙ_ФАЙЛ"}
   ```

   Для управляемого VPS путь — `/var/lib/studio1925/settings/telegram-bot.json`. Каталог `settings` — 0700, файл — 0600, владелец/группа `studio1925`. Symlink, hardlink, доступ группе/остальным и конфигурация внутри приложения отклоняются. В SQLite токена нет. Альтернативный абсолютный путь задаёт `TELEGRAM_CONFIG_FILE`; для переносимости установщика и backup используйте стандартный путь.
4. Обработчик замечает появление файла без перезапуска сайта (обычно в пределах 5 секунд), проверяет `getMe`, сохраняет **только** bot ID/username. Для Telegram нужны исходящие HTTPS и рабочий DNS. Unit использует read-only bind существующего `/etc/resolv.conf` внутрь своего RootDirectory; host DNS, firewall и другие службы не изменяются. Если исходящий доступ запрещён, согласовать его отдельно.

Стандартный файл настроек остаётся вне release, переживает обновление и входит в существующий **зашифрованный** backup вместе с SQLite. Следовательно, доступ к архиву и ключу позволяет восстановить токен: защищайте их, plaintext-временные файлы и recovery-каталоги. Ротация токена того же бота поддержана; обработчик перечитывает файл и начинает новую сессию. Другой bot ID блокируется `BOT_CHANGED_RELINK_REQUIRED`: независимый бот требует отдельно согласованной перепривязки получателей, а не автоматического доверия старым ID.

## Локальное управление и первая привязка

Публичного bootstrap API нет. Оператор должен уже иметь санкционированный доступ к ОС и приватной базе. `--local-operator` — явное подтверждение локальной операции, **не** замена прав ОС. Процесс проверяет владельца и права каталога/SQLite. У `studio1925` нет login shell/sudo.

В локальной разработке после `db:init`, `db:migrate`, создания защищённой конфигурации и запуска `dev:server`:

```bash
npm run telegram -- status
npm run telegram -- bootstrap-owner --local-operator --invite-file /absolute/private-invites/owner.txt
```

Родительский каталог приглашений создайте заранее с 0700 под тем же UID, **вне checkout и вне `settings`**, чтобы plaintext-приглашения не входили в backup. Файл создаётся только новым, с 0600, EXCL/NOFOLLOW. CLI выводит только внутренний ID и срок, но не ссылку.

Для управляемого VPS root-оператор может запускать CLI в том же изолированном release, без редактирования managed env. Следующий локальный helper — пример ручных команд, не автоматический workflow и не команда установки:

```bash
# Root shell на согласованном сервере. Не использовать set -x.
studio_release=$(python3 -c 'import json; print(json.load(open("/etc/studio1925/state.json"))["current"])')
studio_root="/opt/studio1925/releases/$studio_release/root"
install -d -m 0700 -o studio1925 -g studio1925 /var/lib/studio1925/private-invites
studio_telegram() {
  systemd-run --quiet --wait --pipe --collect \
    --property=User=studio1925 --property=Group=studio1925 \
    --property="RootDirectory=$studio_root" --property=WorkingDirectory=/app \
    --property=BindPaths=/var/lib/studio1925:/data \
    --property=UMask=0077 --property=NoNewPrivileges=true \
    --property=ProtectSystem=strict --property=PrivateTmp=true \
    --property=RuntimeMaxSec=60 \
    --setenv=APP_MODE=server --setenv=SQLITE_PATH=/data/studio.sqlite \
    /usr/bin/node --conditions=react-server scripts/telegram.mjs "$@"
}
studio_telegram status
studio_telegram bootstrap-owner --local-operator --invite-file /data/private-invites/owner.txt
```

Если `botReady=false`, сначала исправьте защищённую конфигурацию/исходящий доступ и подождите `getMe`. Откройте файл приглашения **локально в защищённом редакторе**, передайте ссылку владельцу приватно, не печатая её в Actions/публичный терминал. Владелец открывает ссылку в Telegram и нажимает Start. Токен действителен час, хранится в базе только SHA-256, одноразовый. Принимается только private message с совпадающими `from.id` и `chat.id`, полученными от официального Telegram API. Ввод произвольного Telegram ID не подключает получателя. Перебор дополнительно ограничен 10 подходящими попытками в минуту на хеш sender ID. Ссылка — bearer secret: украденный токен может привязать чужого человека, поэтому передавайте его только адресату.

Повторите `status`: получатель должен стать `connected`. Первая запись владельца создаётся только один раз. Если ссылка истекла/потерялась, возьмите внутренний ID из статуса и используйте `renew`, не пытайтесь повторять bootstrap и не редактируйте таблицы вручную. После использования удалите plaintext-файл приглашения своим обычным безопасным процессом работы с секретами.

## Сотрудники, тест и выключение

Здесь `RECIPIENT_UUID` — внутренний ID из CLI, не Telegram ID. Используйте `npm run telegram -- …` локально или `studio_telegram …` на управляемом сервере:

```bash
studio_telegram enable --local-operator
studio_telegram test --local-operator --recipient RECIPIENT_UUID
studio_telegram status
studio_telegram recipient-off --local-operator --recipient RECIPIENT_UUID
studio_telegram recipient-on --local-operator --recipient RECIPIENT_UUID
studio_telegram revoke --local-operator --recipient RECIPIENT_UUID
studio_telegram disable --local-operator
```

`test` создаёт одно задание с техническим текстом без клиентских данных и использует обычную очередь/повторы. Он требует включённых уведомлений и активного подключённого получателя. Проверяйте результат в своём Telegram и техническом статусе; успешное создание задания ещё не означает доставку. `disable` останавливает уведомления, не останавливая бронирования. Для немедленного прекращения доступа конкретного сотрудника используйте `recipient-off` либо `revoke`, а не только глобальную паузу.

Новое приглашение: подготовьте приватный файл 0600 с единственным полем `{"displayName":"Имя сотрудника"}` и выполните `invite --local-operator --details-file /data/private-invites/person.json --invite-file /data/private-invites/person-link.txt`. Обновление: `renew --local-operator --recipient RECIPIENT_UUID --invite-file /data/private-invites/new-link.txt`; старый неиспользованный токен отзывается, существующая привязка и ожидающие отправки отменяются до нового подключения. Количество получателей не ограничено произвольным маленьким числом.

## Безопасность, администрирование и восстановление

`TelegramAdministration` предоставляет список получателей, приглашение/перевыпуск, включение/выключение, отзыв доступа, тест, статусы и постраничную историю технических ошибок. Каждый метод требует проверенного сервером authenticated principal с правом `telegram:manage`. Будущая панель должна передать **реальную проверку серверной сессии/прав**, а не доверять JSON из браузера. Telegram-подключение не выдаёт права входа в веб-панель. Самой панели, web-авторизации, HTTP admin endpoints и управления бронями через бота в этом PR нет.

В уведомление передаются имя, фамилия, телефон, дата/интервал клиента. Это согласованная передача персональных данных стороннему сервису Telegram; до production-включения владелец определяет основание обработки, уведомление клиента, круг сотрудников, сроки хранения и применимые требования закона. Отзыв сотрудника не удаляет полученные им сообщения. Технические логи содержат только ограниченные коды, без Telegram ID, текста, ссылок и токена. Bot API вызывается нативным HTTPS-клиентом с проверкой TLS и фиксированным endpoint, без Next fetch tracing, redirect и parse_mode; пользовательский текст выводится буквально, управляющие символы убираются.

Обновление — только существующим проверенным установщиком с обязательной копией. Миграция добавляет таблицы/триггеры без изменения бронирований. Схемный откат не объявляется безопасным без проверки совместимости: сохранить backup и применять штатный restore. Очередь, recipients, hashes, update offset и переключатель входят в SQLite backup; бот-файл — в settings backup. На новом VPS восстановить **оба** вместе с правами 0700/0600, а не один файл live SQLite при WAL.

Рабочий бот должен иметь **один активный VPS/одну базу**. SQLite lease не координирует две независимые восстановленные копии: перед активацией recovery-сервера остановите исходный Studio либо отключите там Telegram и уберите конфигурацию бота согласованной процедурой. Иначе возможны конкурирующий polling и дубли. После restore обработчик ждёт истечения прежнего lease (до 60 секунд), продолжает pending и не отправляет за пределами 24 часов. Не восстанавливайте старую копию только ради повторной доставки уже принятых сообщений.

Автоматические проверки используют вымышленные данные и подмену Telegram транспорта. Реальная отправка, production-конфигурация и действия на VPS этим PR **не выполняются**. Уведомления можно безопасно оставить выключенными до отдельной настройки и приёмки.
