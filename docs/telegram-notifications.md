# Telegram: настройка через Actions и управление в боте

Бронирования работают независимо от Telegram. Уведомления по умолчанию приостановлены. Клиентский интерфейс, API бронирований, HTTPS, установщик и VPN не меняются. Этот PR не включает функцию на рабочем сервере.

## Первоначальная настройка без терминала

Действия выполняет технический администратор **после согласования PR и штатного обновления Studio**, а не во время разработки.

1. Создайте одного бота через официальный `@BotFather` → `/newbot`. Сохраните его username. Если бот уже использовался другим процессом, сначала остановите прежнюю эксплуатацию и перевыпустите токен в BotFather. Токен выдаёт доступ к боту; не присылайте его в чат разработки, issue или Actions input.
2. В GitHub репозитория откройте **Settings → Secrets and variables → Actions → New repository secret**. Имя: `STUDIO_TELEGRAM_BOT_TOKEN`, значение: токен BotFather. Существующий `STUDIO_SSH_PASSWORD` остаётся без изменений.
3. Откройте **Actions → Manage Studio Telegram → Run workflow**, ветка `main`. Введите IP установленной Studio (IPv4 или IPv6), operation `configure`, confirmation `CONFIGURE STUDIO TELEGRAM`. Никаких токенов в поля запуска не вводите.
4. Дождитесь SUCCESS: `configured`, `instanceBound`, `botRegistered`, `workerLive` должны быть `true`, `workerState=RUNNING`. Проверяются официальный `getMe`, отсутствие webhook и фактический успешный long polling с текущей конфигурацией. Успешный `getMe` сам по себе не считается готовностью.
5. В собственном **личном** чате с ботом нажмите Start. Затем выберите команду `/owner` в меню команд Telegram. Она нужна только для первой привязки. Start не подписывает и не назначает владельца.
6. Бот отправит вам код, действующий 15 минут. В Settings → Secrets and variables → Actions создайте временный Secret **`STUDIO_TELEGRAM_OWNER_CONFIRMATION`** с этим кодом. Не публикуйте его в Summary, inputs, переписке или скриншотах. Если первый владелец другой человек, получите именно его код по доверенному личному каналу и проверьте адресата.
7. Запустите workflow с operation `bootstrap-owner`, confirmation `INITIALIZE STUDIO TELEGRAM OWNER`, тем же IP. Дождитесь `ownerReady=true` и сообщения владельцу в Telegram. После успешного подтверждения удалите временный Secret.
8. В Telegram нажмите **Управление студией → Рассылка → Включить**. Если хотите лично получать брони, отдельно нажмите **Подписаться на рассылку**. Собственная подписка владельца одобряется автоматически. В **Тест сообщения** проверьте доставку технического сообщения без данных клиентов.

Первым владельцем становится только аккаунт, код которого явно подтвердил администратор, имеющий право запускать workflow и менять Secrets. У других пользователей тоже может быть собственный код, но без этого подтверждения он не даёт полномочий. Код связан с проверенным Telegram user ID, хранится в SQLite только SHA-256, одноразовый, формируется с серверным секретом. Plaintext не хранится даже в управляющей очереди — worker формирует его непосредственно перед отправкой адресату. Повтор после потери результата с тем же уже подтверждённым кодом безопасен. После назначения владельца новые bootstrap-подтверждения другого аккаунта запрещены.

## Действия сотрудника

- `/start` показывает две кнопки: **Подписаться на рассылку** и **Отключить рассылку**. Сам Start доступа к бронированиям не даёт.
- Подписка создаёт одну pending-заявку. Владельцу независимо от его собственной подписки и паузы приходит имя/username отправителя с **Одобрить / Отклонить**. Username используется только как подпись, никогда для авторизации.
- Повторное нажатие не создаёт новую заявку или повторное уведомление владельцу. Действуют ограничения частоты, а не маленький лимит числа сотрудников.
- Одобрение открывает только новые уведомления, без рассылки старых броней. Отклонение сообщает об отказе.
- Самостоятельное отключение немедленно отменяет ожидающие задания и заявку, сообщает владельцу. Повторное подключение требует нового одобрения.
- Pending-заявка действует 7 дней. Кнопки действуют 15 минут; устаревшее решение не исполняется — владелец открывает «Заявки» заново.

## Меню владельца

| Раздел | Возможности |
| --- | --- |
| Сотрудники | Постраничный список и статус подписки; отключение; удаление доступа с отдельным подтверждением. Уведомление сотруднику, если Telegram принимает сообщения. |
| Заявки | Одобрение/отклонение актуальной pending-заявки ровно один раз. |
| Рассылка | Приостановка/возобновление бронирований; приём броней остаётся доступен. |
| Тест сообщения | Технический тест самому владельцу без данных клиентов, доступен и без его подписки. |
| Статус системы | Heartbeat worker, число подписчиков/заявок, очередь и число ошибок/истёкших доставок. Без токенов и телефонов клиентов. |
| Передача прав | Выбор пользователя, уже открывшего бота, подтверждение текущим владельцем и принятие новым. |

Удаление логическое: доступ отзывается, историческая запись остаётся для ссылок и аудита. Повторная подписка создаёт новую pending-заявку. Старые решения и отменённые доставки не оживают.

Один главный владелец задаётся одной ссылкой в SQLite. Его административная роль и активная подписка независимы. Отключение своей подписки не лишает прав. Административные сообщения не содержат контактных данных бронирований и отправляются через отдельную небольшую SQLite-очередь тем же worker, даже при паузе рассылки. Новые брони идут только активным подтверждённым подписчикам.

## Передача бизнеса и замена токена

1. Новый владелец открывает бота и нажимает Start; подписываться для получения прав необязательно.
2. Текущий владелец: Управление студией → Передача прав → выбрать человека → Подтверждаю передачу.
3. Новый владелец принимает предложение в личном чате в течение 15 минут. Отказ или истечение срока оставляют прежнего владельца. Удаление кандидата аннулирует предложение.
4. Роль меняется одной SQLite-транзакцией. Прежний владелец сразу теряет административные права и старые кнопки; подписки всех сотрудников остаются без изменений. Проверьте меню нового владельца. Он отдельно решает, получать ли бронирования.
5. Передайте самого бота через BotFather по его текущей процедуре. Это отдельная операция Telegram, не передача VPS/GitHub/домена.
6. Новый собственник перевыпускает токен **того же бота** и передаёт его техническому администратору защищённым каналом. Администратор заменяет Secret `STUDIO_TELEGRAM_BOT_TOKEN` и запускает `rotate-token` с confirmation `ROTATE STUDIO TELEGRAM TOKEN`.
7. Workflow сначала проверяет токен официальным API и совпадение числового bot ID. Неверный токен, другой бот или webhook блокируют запись; прежний файл не заменяется. Верный токен записывается атомарно; worker перечитывает его без рестарта сайта. Успех объявляется только после polling именно с новым отпечатком конфигурации.
8. Проверьте diagnose и технический тест в меню нового владельца. Переподключать сотрудников и пересоздавать SQLite не требуется. У прежнего владельца могут остаться права подписчика, но не администратора; новый владелец может отдельно отозвать и подписку.

Новый токен нельзя установить обычным `configure`: используйте явный `rotate-token`. Глобальная настройка рассылки, очередь, роли, signing key и подписчики не сбрасываются. GitHub/VPS/резервное копирование остаются у технического администратора.

## Диагностика, неизвестный результат и права workflow

`diagnose` не требует token/confirmation inputs и не меняет настройки VPS. Summary выводит только флаги, счётчики и ограниченный код worker. IP маскируется, Telegram ID/имена, код подключения, токен и отпечатки не печатаются. Успешный diagnose с `workerLive=false` означает завершённую проверку, **не** работоспособность бота.

При SSH/Telegram/GitHub ошибке workflow не сообщает успех. Сначала повторите **diagnose на том же VPS**. Если запись конфигурации завершилась, но потерян ответ/не завершена запись реестра, diagnose может подтвердить её только по совпадающим отпечаткам и живому polling и завершить исключительно запись метаданных GitHub. При неверном токене или другом bot ID старая конфигурация остаётся на месте. Если новый правильный токен уже записан, но Telegram недоступен, конфигурация сохраняется для диагностики: бронирования продолжают работать.

Workflow доступен только из main с четырьмя успешными обязательными проверками этого SHA; GitHub permissions `contents:read`, `actions:read`, `deployments:write`. Передача пароля — существующая политика Studio root:22 через `sshpass -e`; только эти SSH-процессы отключают host-key checking. **Сохраняется риск MITM и передачи root-пароля/настроек подставному серверу.** Глобальный SSH и настройки VPS не изменяются.

На VPS выполняется короткий transient `systemd-run` под существующим `studio1925`, в установленном RootDirectory и с доступом к `/data`. Нет второй постоянно работающей службы. Перед и после проверяются принадлежность релиза, закрытые пути и состояние существующей службы. Job использует существующую concurrency-группу `studio-install-<server_ip>` на всё время операции, а workflow — отдельную общую группу реестра. Так стандартные install/update/backup/restore/HTTPS для того же IP не вклиниваются между plan, записью реестра и проверкой polling. Дополнительно каждый root-вызов берёт существующий installer lock. Используйте одно и то же каноническое написание IP во всех workflows; ручные операции и альтернативные записи IPv6 вне общей группы могут завершиться отказом/неопределённым результатом, но не успехом. Токен/код идут только по SSH stdin в CLI stdin, не argv/файлы runner/артефакты. Код CLI уже входит в стандартный релиз. Старые защищённые локальные CLI сохранены для совместимости, обычному владельцу они не нужны; публичных admin API нет и веб-панель не планируется этим этапом.

## Один бот — один активный VPS

Без внешнего координатора SQLite lease защищает только одну базу. Поэтому используются **уже имеющиеся** GitHub Deployment metadata с environment `studio-telegram`: bot/instance/token SHA-256 без токена, кода или персональных данных, плюс общая concurrency-группа workflow. Это не deployment приложения и не новый сервис. Конфигурация резервируется в реестре до записи на VPS; неопределённая незавершённая операция блокирует перенос, а не разрешает второй polling.

Дополнительно конфигурация связана со случайным локальным `/var/lib/studio1925/.telegram-instance` (0600), который не входит в существующий backup. Runtime его только читает. Восстановленная штатным restore конфигурация (включая прежний VPS) сама по себе **не запускает** Telegram (`INSTANCE_MISMATCH`), но бронирования работают. Один и тот же токен нельзя зарегистрировать на втором instance. Для повторной активации после restore/согласованного переноса нужно восстановить SQLite/settings, перевыпустить токен того же бота в BotFather и выполнить `rotate-token` на новом VPS. Старый токен становится недействительным. При неизвестном исходе прежней настройки сначала подтвердите его на прежнем VPS; не обходите pending-реестр.

Telegram `409` при конкурентном polling останавливает эту сессию до изменения конфигурации; отправки новой сессии не начинаются до успешного polling. Новый ключ не отменяет уже принятые Telegram сообщения.

Граница гарантии: реестр координирует поддержанные workflows **этого репозитория**, а не произвольные ручные копии root или другой GitHub-репозиторий. При первом принятии ранее использовавшегося бота обязательно перевыпустите токен, чтобы исключить неизвестную старую установку. Root-доступ и Secrets дают технические полномочия и должны оставаться только у доверенных администраторов. Изменение environment/удаление записей реестра вручную не является поддержанным способом переноса.

## Хранение, доставка, обновление и backup

- Миграция `0004_telegram_subscriptions.sql` добавляется после неизменённых 0001–0003; сохраняет bookings, приглашения, update offset и существующую очередь. Новые таблицы: заявки, bootstrap-хеши, передачи роли, одноразовые UI-действия/ограничение частоты, управляющая очередь. Настройка нового bot ID не разрешена.
- Бот работает внутри существующего Next.js через instrumentation при SERVER/`STUDIO_TELEGRAM_WORKER=1`. DEMO и сборки его отключают. В SQLite — роли, пользователи, очередь, хеши; токен и signing key — только в стандартном защищённом `settings/telegram-bot.json` v2. Каталог 0700, файл0600, атомарный rename/fsync, отбрасываются symlink/hardlink/чужие права. Legacy v1 не теряется, но требует нового `configure` для безопасной настройки меню/host binding.
- Новая бронь и задания активным получателям записываются в одной транзакции существующим trigger; unique booking/recipient и requestId сохраняют защиту от дублей. Telegram не меняет статус брони.
- Отправки/long polling/heartbeat работают независимо в одном worker. Polling offset, изменения от update и управляющие ответы COMMIT вместе: ошибка записи откатывает и offset. Lease60с, heartbeat10с; перезапуск продолжает очередь.
- Общая частота не чаще1,1с, 429 учитывает retry_after, временные ошибки backoff до15мин. Общий срок booking/control задания не дольше24ч; callback-ack30с. Нельзя возобновить просроченное сообщение паузой/перезапуском. При возобновлении отправляются только актуальные задания. Постоянные ошибки заканчивают попытки.
- Проверка подписки/паузы и начало HTTP-запроса находятся под короткой writer-транзакцией без ожидания сети. Отзыв, закоммиченный первым, исключает начало отправки. Уже начатую отправку гарантированно отменить нельзя; полученное сообщение невозможно отозвать. После сетевой неопределённости Telegram может получить дубль — Bot API не гарантирует exactly-once.
- Управляющие callbacks подписаны HMAC, привязаны к actor/epoch/version, срок15мин, одноразовые; каждый admin action повторно читает текущую роль из SQLite. При передаче прав ожидающие owner-only сообщения старой роли отменяются. Приглашения PR27 не становятся публичным механизмом самоназначения.
- Очередь, пользователи, роли, хеши и cursor входят в SQLite backup. Конфигурация v2/signing key входят в существующий **зашифрованный** settings backup. Защищайте recovery-каталоги и ключи архивов; не публикуйте расшифрованные файлы. Обычное обновление сохраняет nonce. Штатный restore заменяет весь каталог данных, поэтому nonce отсутствует и на прежнем, и на другом VPS: Telegram остаётся безопасно выключенным до перевыпуска токена того же бота и `rotate-token`. Роли/подписки/очередь/signing key восстановлены из копии; пропущенные сообщения всё равно ограничены24часами. Не копируйте nonce из recovery вручную и не редактируйте реестр в обход этой процедуры.
- Обновление и restore — существующими проверенными workflows, с backup и проверкой совместимости схемы. Миграция аддитивная; откат к версии до0004 может быть несовместим и не объявляется безопасным без штатной проверки. Не копируйте live SQLite простым cp при WAL. Этот PR не меняет шифрование/backup/restore и не выполняет их на production.

## Данные и ограничения production

Сообщение о бронировании содержит ФИО, телефон и московский интервал клиента: это передача контактов в Telegram. **До включения production** собственник определяет законное основание, уведомление клиента, допущенных сотрудников и сроки хранения. Неподтверждённые сотрудники не получают контактов. Технические сообщения/логи/Actions не содержат контактов, секретов и raw Telegram errors; транспорт — фиксированный официальный HTTPS API с TLS-проверкой, без Next fetch tracing и parse_mode.

Автотесты используют вымышленные контакты и подменённый Telegram API. Реальные бот, VPS, SQLite production и уведомления этим PR не затрагиваются. Веб-администрирование, Telegram-управление бронями, новые порты, конфигурация Caddy/UFW/DNS/SSH и развёртывание не входят в работу.
