# Studio 19.25 — установка, резервирование и восстановление (2.5.2)

Пакет теперь дополнительно проходит обязательный browser/SQLite gate из его
распакованного root filesystem на x64 и ARM64, в localhost и insecure HTTP context.
Подробности: [booking-confirmation-recovery.md](booking-confirmation-recovery.md).

Подготовлено для приёмки PR. **Реальных SSH-подключений, установки на VPS и записи в рабочий backup-репозиторий в рамках этого PR не было.** Установщик не зависит от IP, страны и провайдера. Merge и первый запуск выполняет владелец после приёмки.

## Подготовка GitHub

1. Создайте **отдельный приватный репозиторий** для копий: GitHub → New repository → Private → Add README. Имя произвольное. Пустой неинициализированный или публичный репозиторий не подходит. Не загружайте архивы через Git: используются только Release assets. Для этого репозитория не включайте immutable Releases и не блокируйте служебные теги `studio1925-*` правилами, запрещающими очистку: workflow должен менять pending metadata и удалять устаревшие копии. Код не отключает защиты автоматически; при запрете API завершится FAILED.
2. В GitHub Settings → Developer settings → Fine-grained personal access tokens создайте отдельный токен: доступ **только к backup-репозиторию**, Repository permissions **Contents: Read and write**, Metadata: Read. Не выдавайте доступ ко всем репозиториям, Actions, администрированию или организации. Учитывайте срок действия и возможное одобрение владельцем организации. Стандартный `GITHUB_TOKEN` приложения не даёт доступа к другому private repo.
3. В `jurist77/loft-booking` → Settings → Secrets and variables → Actions создайте следующие **Secrets**. Не передавайте значения в чат, PR, issue или Run workflow.

| Secret | Назначение |
| --- | --- |
| `STUDIO_SSH_PASSWORD` | Существующий root-пароль выбранного VPS; SSH:22. Установщик не разрешает root/password login, если он запрещён сервером |
| `STUDIO_BACKUP_TOKEN` | Выделенный fine-grained токен из п. 2 |
| `STUDIO_BACKUP_PASSPHRASE` | Случайная длинная парольная фраза для AES-256, минимум 32 символа, без перевода строки; сохраните независимую защищённую копию вне GitHub |

4. На вкладке **Variables** создайте `STUDIO_BACKUP_REPOSITORY` со значением `владелец/приватный-репозиторий` и `STUDIO_BACKUP_SERVER_IP` с IP ежедневного резервирования. Это настройки GitHub, адреса в исходниках отсутствуют. Для другого VPS меняются IP и пароль; не меняйте Secrets во время выполняющейся операции. Один набор настроек обслуживает одну студию, не парк серверов.
5. В GitHub Settings → Notifications → Actions включите уведомления о неудачных workflows и проверьте доставку email. Failed run и Summary — встроенное уведомление GitHub; без настроек аккаунта доставка email не гарантируется.
6. После приёмки объедините PR самостоятельно. Workflows запускаются только из `main`; до merge кнопки Run workflow в default branch может не быть. Дождитесь успешных последних проверок **точного SHA main**: Backend, VPS audit и Installer.

Парольная фраза не ротируется простым изменением Secret: старые копии требуют прежнего ключа. Потеря ключа делает их невосстановимыми. Токен имеет право удалить копии — его компрометация опасна даже при шифровании. GitHub Releases не заменяют независимую архивную копию ключа и периодическую проверку восстановления.

## Install Studio 19.25

Actions → **Install Studio 19.25** → Run workflow → Branch **main** → единственное поле `server_ip` → Run workflow. Вводите голый IPv4 или IPv6, без схемы, порта, скобок и DNS-имени. Input не является Secret, IP может быть виден в метаданных Actions.

Ставится зафиксированный проверенный SHA main на момент запуска. Push сам по себе **не выполняет SERVER-deploy**. Production-пакеты собираются и испытываются на одноразовых Ubuntu 24.04 x64/ARM64 runners; VPS не выполняет npm/Next build, apt install/upgrade, не получает backup-токен или ключ шифрования.

Операции:

- **Нет установки:** проверка ОС/архитектуры/ресурсов и чужих путей, отдельный пользователь, релиз, SQLite init/migrate/check, systemd, health, техническая приёмка.
- **Тот же исправный SHA:** `already-current`, без переустановки и перезапуска рабочего сайта; проверяются service/API/изолированный тест. Нездоровый сайт не получает ложный SUCCESS.
- **Новый SHA:** остановка только Studio, согласованный снимок SQLite/photos/settings, шифрование на runner, upload и обратное скачивание/hash verification в private Releases. Только после этого разрешаются миграции и переключение релиза. До подтверждения копии сайт удерживается остановленным, чтобы не появлялись записи вне checkpoint. При ошибке резервирования возвращается прежний сайт, если схема не менялась; обновление запрещено.
- **Ошибка:** новый сайт останавливается. Возврат старого кода разрешён только при неизменных схеме и журнале миграций и успешных проверках старого релиза. Иначе сайт остаётся остановленным с `manual-required`; данные и защищённая pre-update копия сохраняются. Схема не откатывается автоматически.

Если связь потеряна при передаче снимка или пакета, coordinator пытается снять hold только по совпадающим nonce и прежней схеме. Если SSH остаётся недоступен, состояние неизвестно: не объявляется ни успех, ни гарантированный откат; данные/закреплённая копия сохраняются. После потери ответа о уже завершённой установке повтор проверяет ready/health и не переустанавливает текущий исправный SHA. После committed несовместимой миграции автоматический возврат старого кода запрещён.

После установки Summary содержит SHA, operation, migrations, active/enabled service, health, техническую приёмку, выбранный порт, URL и **отдельный** `public_access`. Обрыв SSH означает неизвестный итог; не запускайте параллельные повторы. Root lock сериализует операции на VPS, GitHub concurrency дополняет его. Прерванное состояние не обходят удалением marker/lock или правкой SQL history.

## Временный HTTP-доступ

Новый согласованный тестовый режим слушает публичный адрес `http://IP:PORT` (IPv6 — `http://[IP]:PORT`). Проверяется 3000, затем 3100–3199; занятые порты не перехватываются. Выбранный порт сохраняется при обновлениях; если его заняла чужая служба, установка отказывает, не останавливая её.

**Только вымышленные контакты. HTTP не шифрует трафик. До HTTPS нельзя вводить реальные телефоны и персональные данные.** Никаких DuckDNS, сертификатов, публичных туннелей или изменений VPN/proxy/firewall/DNS этот PR не делает. SERVER использует точный Origin IP:port и явный `API_ALLOW_INSECURE_TEST_HTTP=true`; обычная конфигурация по-прежнему запрещает non-loopback HTTP. CORS, rate limits и недоверие к произвольному X-Forwarded-For сохранены.

`health=200` означает исправность на VPS. `public_access=unreachable` означает, что запрос с runner не подтвердил внешний доступ: возможны firewall/провайдер/IPv6-маршрут. Это **не повод** автоматически менять сеть; потребуется отдельное согласование. Не считать внутренний SUCCESS доказательством публичной доступности. Для первой приёмки откройте **точный URL из Summary**, пройдите пять экранов с вымышленными контактами.

## SSH и root-права

По согласованному решению владельца **все операции Studio: install, daily backup, pre-update backup и restore** используют одну политику: `StrictHostKeyChecking=no`, `UserKnownHostsFile=/dev/null`, `GlobalKnownHostsFile=/dev/null`, `UpdateHostKeys=no`, `-F /dev/null`. Это параметры отдельного SSH-процесса внутри workflows Studio, а не изменение глобальных настроек runner/VPS или обычного SSH владельца. Дополнительный Secret с ключами хоста не требуется. **MITM или ошибочный IP могут передать root-пароль подставному серверу, подменить команды/данные и получить доступ к архиву до его шифрования. SHA256 артефакта и шифрование offsite-копии не подтверждают подлинность SSH-сервера и не устраняют этот риск.** Сверяйте адрес через доверенную панель провайдера.

Пароль передаётся sshpass через отдельное окружение `SSHPASS`, не argv/файлы/артефакты/логи. Raw SSH stderr, SQL, клиентские строки и env не печатаются. Root нужен только для проверки совместимости, managed user/каталогов/прав, доставки, unit и запуска собственных sandbox CLI/systemd. Next работает как `studio1925` без sudo и дополнительных групп. SSH-политика, VPN, сторонние службы и сетевые настройки не редактируются и не перезапускаются.

| Путь | Назначение |
| --- | --- |
| `/opt/studio1925/releases/…` | Root-owned код, Node и native libraries; текущий релиз указан в атомарном root-only state, отдельный current symlink не требуется |
| `/var/lib/studio1925/` | Постоянные `studio.sqlite`, `photos/`, `settings/`, каталог 0700; файлы 0600 |
| `/etc/studio1925/` | Root-only server.env/state; DB/contacts не в конфигурации релиза |
| `/var/backups/studio1925/` | Локальные checkpoint/временные снимки, закрыты от других пользователей |
| `/var/cache/studio1925/` | Writable cache внутри sandbox |
| `studio1925.service` | RootDirectory, минимальные bind mounts, read-only code, private host filesystem, restart и boot enable |

При первой установке photos получает существующие изображения; обновления их не перезаписывают. Settings — основа хранения, а не административный редактор: пока `studio.json` не подключён как новый UI. Логотип, тексты, пять экранов и правила бронирования не меняются. RootDirectory не позволяет приложению читать файлы VPN, включая world-readable canary в CI.

## Ежедневное резервирование

Workflow **Back up Studio 19.25**: cron `15 0 * * *`, то есть **03:15 Europe/Moscow**; ручной запуск — необязательный IP, иначе `STUDIO_BACKUP_SERVER_IP`. GitHub cron может задерживаться и отключаться при неактивности публичного репозитория: это не SLA. Проверяйте свежесть успешных runs и копий.

Снимок согласован: только сайт кратковременно останавливается, SQLite снимается существующим **Backup API**, одновременно копируются photos/settings, затем сайт возобновляется **до** шифрования и сетевой загрузки. Пароль/токен/ключ не включаются в snapshot. Архив содержит manifest с версией, schema/history fingerprint, SQL checksums, полным списком файлов/размеров/SHA256. Файлы с symlink/hardlink, пути за пределами дерева и неизвестные элементы отклоняются.

На runner: GPG AES-256 + SHA-512 S2K, ключ через файловый дескриптор; private temporary home и файлы очищаются. В Releases попадает только `snapshot.tar.gz.gpg`, без plaintext artifacts. После upload файл скачивается обратно и сравнивается SHA256; лишь затем draft публикуется как verified. Выполняется максимум две попытки ежедневного резервирования; затем FAILED/уведомление GitHub. Ошибка сети/шифрования не оставляет сайт намеренно остановленным; если сам service не может возобновиться, run завершается ошибкой, а не обещает доступность.

Политика для **одной студии, включая переезд на другой VPS**:

- Последняя успешная daily за каждый из последних **7 дней с успешными копиями по Москве**; повтор за тот же день заменяется только после проверки новой копии.
- Последние **3 завершённые pre-update**; копия незавершённого обновления закреплена и не удаляется. Одна незавершённая копия на instance блокирует следующее обновление до безопасного завершения/восстановления. После подтверждённого healthy commit или безопасного возврата закрепление снимается.
- Очистка только собственного namespace `studio1925-*`, Releases/assets и связанных тегов; чужие Releases не затрагиваются. Сначала удаляется тег, затем Release с архивом: при ошибке API Release остаётся видимым, и следующий запуск может завершить очистку. HTTP 404 допускается только как отсутствие уже удалённого объекта; 403/5xx и транспортные ошибки не скрываются. Неудачный новый backup не удаляет прежнюю успешную копию. Непроверенный draft своего запуска удаляется по возможности; API-ошибка очистки видима как FAILED и требует проверки.

GitHub допускает Release asset **меньше 2 GiB**, число assets ограничено 1000 на release; здесь один файл и лимит **1900 MiB**, плюс ограничение исходных данных **1500 MiB**. Лимит размера проверяется до upload; бесконечное хранилище не обещается. См. [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases), [Release API](https://docs.github.com/en/rest/releases/releases), [fine-grained permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens). Код проверяет private/write/default-branch, upload/readback/delete API. **Реальные разрешения токена, квоты и запись в backup repo в этом PR намеренно не проверялись**: внешние операции заменены тестовым адаптером; перед эксплуатацией нужен отдельно разрешённый пробный backup/restore.

## Restore Studio 19.25

1. Actions → **Restore Studio 19.25** → Run workflow → main → `operation=list`. Получите список проверенных tags, версий и pending. Этот режим не подключается к VPS и ничего не меняет.
2. Выберите точный tag. Запустите снова с `operation=restore`, `server_ip`, `backup_tag`, `confirmation=RESTORE STUDIO 19.25`. Необязательный `app_version` — полный проверенный main SHA; по умолчанию текущий SHA. Вводы IP и tag не секретные.
3. До подключения к VPS проверяются подтверждение, CI принятого SHA, скачивание/hash/decrypt и архив. Сборка создаётся под обе архитектуры, выберется соответствующая целевому VPS. Проверка host key **отключена**, как и при install/backup; для другого VPS заранее обновите SSH-пароль в Secret и проверьте IP.
4. На целевом VPS проверяются точное соответствие checksums миграций и fingerprint схемы, реальная целостность DB через штатный CLI. Неподходящая версия не применяет миграции к snapshot «наугад»: выберите проверенный совместимый SHA, поддерживающий этот формат установщика. Произвольные исторические версии не гарантированы.
5. При существующей установке сначала пытается сохранить текущее состояние во внешней зашифрованной копии. Если из-за повреждённой DB это невозможно, **только явно подтверждённое restore** допускает сохранение исходного каталога локально. Снимок целиком меняется через соседний каталог на том же диске; исходные SQLite/WAL/photos/settings остаются в `studio1925-recovery-*`. Это не автоматический обход барьера обычного update.
6. После restore проверяются service/API/DB и изолированная техническая приёмка. При ошибке возвращается исходный каталог и только совместимый старый код. Неудачный incoming snapshot сохраняется отдельно для разбора. При небезопасном возврате сайт остаётся остановленным; backups/оригинал не удаляются. Серверные настройки Origin/IP создаются заново; credentials из чужого VPS не восстанавливаются.

Можно восстановить на другом совместимом VPS; шифрование независимо от CPU, пакет пересобирается под целевую архитектуру. DATA как отдельный mountpoint для атомарной замены сейчас не поддерживается — отказ до swap. Восстановление более старой копии возвращает данные на её дату: позднейшие записи остаются в сохранённом оригинале, но не сливаются автоматически. Сначала оцените эту потерю актуальности. Ни повреждение DB, ни ошибка health сами по себе не запускают restore без владельца.

## Совместимость, ошибки и эксплуатационные границы

Ubuntu 24.04, полноценный systemd, Python 3.12+, root SSH:22; CPU x86_64/aarch64, штатные namespaces/RootDirectory. Runtime Node 24.12.0/ABI 137 и native better-sqlite3 из lockfile входят в артефакт; Node хоста не меняется. Нужна локальная persistent FS ext4/xfs/btrfs/zfs; tmpfs/overlay/NFS/FUSE отклоняются. Пакеты на VPS не устанавливаются — отсутствующий базовый инструмент даёт понятный отказ.

Admission: минимум 512 MiB MemAvailable и запас диска под code/data/backup/staging, не гарантия VPN-пиков. Потребление памяти конкретного VPS ещё не измерено. Сайт имеет пониженные CPU/IO weights и положительный OOMScoreAdjust; надёжность SQLite WAL/FULL не ослабляется, жёсткий MemoryMax не придуман. [Read-only аудит](vps-audit-runbook.md) нужен перед реальным запуском.

| Ошибка | Действие |
| --- | --- |
| `MAIN_*`, `*_CHECKS_NOT_SUCCESSFUL` | Дождаться проверок точного принятого main SHA |
| `INVALID_SERVER_IP`, `*_MISSING` | Исправить input/Secrets/Variables без отправки секретов в логи |
| `SSH_AUTH_FAILED`, `SSH_CONNECTION_FAILED`, `SSH_TIMEOUT_OR_TRANSPORT_FAILED` | Проверить существующий root:22/маршрут/пароль; sshd/firewall не меняются |
| `ARTIFACT_*`, `NATIVE_*`, `SANDBOX_*`, `UBUNTU_*`, `ARCH_*` | Неподходящая платформа/сборка; не отключать проверки |
| `MEMORY_*`, `DISK_*`, `SNAPSHOT_TOO_LARGE` | Недостаточно ресурсов/превышен лимит; не удалять VPN/брони |
| `PRIVATE_WRITABLE_*`, `BACKUP_*`, `ENCRYPTION_FAILED` | Проверить private repo/token/ключ/лимиты; update без копии запрещён |
| `PREVIOUS_UPDATE_BACKUP_PINNED` | Разобрать незавершённое обновление, не удалять защищённую копию |
| `UNMANAGED_*`, `*_CHANGED_*`, `MAINTENANCE_*`, `INSTALL_ALREADY_RUNNING` | Чужие файлы/изменения/state/lock; не принуждать overwrite |
| `RESTORE_*`, `DECRYPTION_FAILED` | Неверный snapshot/ключ/версия/подтверждение; live данные не подменяются |
| `MIGRATION_FAILED`, `APP_*`, `TECHNICAL_ACCEPTANCE_FAILED` | FAILED + безопасный rollback либо остановка/manual-required; не редактировать migration history |

Релизы приложения, локальные checkpoint и recovery-каталоги автоматически не вычищаются: они могут содержать единственные данные после сбоя. Их рост контролируется admission; нужна будущая согласованная maintenance-политика. При отказе удаления после COMMIT приложение уже обновлено: workflow показывает FAILED, но не откатывает рабочие данные только из-за ошибки GitHub. Retention может временно превысить лимит до успешной повторной очистки; не игнорируйте уведомление. Глобальная ротация journal/VPN не меняется. GitHub schedule и email не являются полноценным мониторингом доступности; systemd не исправляет full disk/corruption. HTTPS, эксплуатационная нагрузка, reboot, реальные права backup repo и end-to-end restore на VPS остаются будущей отдельной приёмкой.
