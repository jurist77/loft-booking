# Read-only атрибуция остатков неудачного HTTPS prepare

После подтверждённой атрибуции и отдельного разрешения владельца: [узкий однократный workflow карантина](https-one-time-quarantine.md). Он сохраняет каталоги и UID/GID, переименовывая dedicated identity вместо удаления. Сам read-only workflow по-прежнему ничего не перемещает и не изменяет.

Расширен существующий **Diagnose Studio HTTPS readiness**. Нового workflow очистки, новых inputs/Secrets или автоматического ремонта нет. Workflow по-прежнему допускает только ручной запуск из main. До принятия этого изменения расширенную проверку VPS не считаем выполненной. Старый отчёт 42670416093 подтверждает только наличие private paths и health=200; это не доказательство их владельцев или содержимого.

## Эталон и предел доказательства

Поддержан ровно один известный случай: [failed apply 42645562662](https://github.com/jurist77/loft-booking/actions/runs/42645562662), исходный коммит `d46d2a067c60560a66176f742f0a094c34871579`, Caddy 2.11.9. Профиль `scripts/diagnostics/https-residue-reference.json` не содержит IP, реального hostname, конфигурации VPS или секретов. Он содержит исторический публичный шаблон и SHA-256:

- control.py — точный результат исторического workflow.source(); установленный код не исполняется;
- caddy и LICENSE — файлы официальных архивов обеих архитектур после проверки закреплённых SHA-256 архивов; найденная архитектура должна совпадать с CPU VPS;
- caddy.json — строгое полное структурное совпадение с историческим renderer для backend :3000, с параметром hostname, дополнительно сверенным по SHA-256 согласованного владельцем адреса этой конкретной попытки. Он извлекается и проверяется только в памяти; неизвестные/повторные ключи и дополнительные настройки блокируют совпадение;
- metadata: root/root BASE и releases, root/TLS-group ETC, TLS/TLS DATA; исторические 0700, файлы 0644/0755/0640, nlink=1, отсутствие дополнительных xattrs/ACL/capabilities. Времена mtime/ctime должны попадать в интервал исходного запуска с допуском 120 секунд. Время само по себе не устанавливает принадлежность.

В CI профиль заново строится из закреплённого исходного коммита и официальных архивов, затем сравнивается целиком (`build_https_residue_reference.py --verify`). Это не выполняет установку.

`MATCHED_FAILED_PREPARE` означает: наблюдаемый snapshot полностью соответствует этому узкому эталону и перечисленным проверкам отсутствия зависимостей. Это сильная техническая атрибуция по нескольким независимым признакам, а не криптографическая квитанция о том, кто записал файлы: прежний prepare такой квитанции не оставил. Компрометированный root или подменённый SSH-сервер вне этой модели доверия. Согласованная SSH-политика без проверки host key сохраняет ранее описанный MITM-риск. Совпадение **не разрешает очистку или apply**.

Любая неопределённость даёт `BLOCKED`, `preservation_required=true`, фиксированную причину и завершённые/незавершённые checks. В Summary нет сырых ошибок, имён неизвестных файлов, числовых UID/GID, hostname, хешей или содержимого конфигураций. Для трёх фиксированных объектов показываются тип, класс владельца/группы и mode bits (448 = 0700).

## Что проверяется без изменений VPS

1. Точное дерево: BASE/{control.py,releases/<pinned archive SHA>/{caddy,LICENSE}}, ETC/{caddy.json}, DATA **пустой**. Неизвестные файлы/директории, symlink, hardlink, спецфайлы или изменённые права блокируют вывод. Любое содержимое DATA, managed.json, transaction.json либо runtime-dir требует сохранения; ключи и сертификаты не открываются.
2. Аккаунт studio1925tls: выделенные системные UID/GID, отсутствие алиасов и дополнительных групп/членов, /nonexistent, nologin. Shadow/пароли не читаются. Аккаунт отсутствует или отличается — BLOCKED.
3. Kernel metadata /proc: процессы с UID/GID/дополнительной группой, exe/cwd/root/open-fd references, mountinfo каждого доступного процесса и текущего namespace. Mount под TLS paths или bind alias из них — BLOCKED. До чтения staging проверяется mountinfo текущего namespace: autofs, FUSE, сетевые и неизвестные filesystem вне пропускаемых /proc, /sys, /dev блокируют обход; таблица mount сравнивается после проверки. Ничьи cmdline/environ не читаются.
4. Ограниченный metadata-only обход файловой системы (без /proc, /sys, /dev, которые проверяются отдельно) ищет UID/GID вне TLS roots, symlink references и повторные mount aliases. Данные приложений, SQLite и VPN не открываются. Из файлов вне TLS читаются только systemd fragments/drop-ins в стандартных системных каталогах, в памяти ищутся ссылки и User/Group; конфигурации не публикуются. Проверяются также загруженные свойства systemd, включая unit, чей файл уже удалён.
5. Лимиты: 45 секунд на аудит, максимум 2 млн entries, 10 тыс. entries в одном каталоге; ограничены размеры всех чтений. Caddy хешируется потоком по 1 MiB. Ошибка доступа, изменение процесса/файла/unit inventory, неполный вывод или лимит = BLOCKED, без попытки обойти ограничение. Файлы и каталоги открываются с NOFOLLOW/NOATIME; нет fallback, меняющего atime.
6. Существующий probe проверяет Studio service/listener/изоляцию/права и штатный health до/после; health косвенно проверяет SQLite без чтения бронирований. Снимок loaded units сравнивается до/после. Занятый 80/443, неработающий health или нестабильный snapshot блокируют положительную атрибуцию. Это не полная проверка содержимого SQLite, резервной копии или функциональности VPN; таких утверждений отчёт не делает.

Обычная работа VPS может вызвать безопасный false BLOCKED (например, новый процесс во время обхода, mount namespace, отказ доступа). Это основание уточнить причину, а не отключать проверку или считать файлы своими. Последующие действия требуют свежего снимка: аудит не удерживает блокировку и не замораживает другие процессы.

## Ручная контролируемая процедура карантина — только проект

**В этом PR ничего из следующего не выполняется. Нет удаляющего/перемещающего скрипта.**

1. После merge владельцем запустить существующий **Diagnose Studio HTTPS readiness → main**, единственный input — прежний server_ip. Проверить `tls_residue`. При BLOCKED не менять ничего; сохранить ссылку и безопасный reason. Для другого исходного commit/артефакта нужен отдельный эталон, а не ослабление этого.
2. Только при MATCHED_FAILED_PREPARE отдельно согласовать точные три source paths, карантин и возможное освобождение имени аккаунта. Запретить параллельные install/update/restore/HTTPS операции на время согласованного окна, использовать существующий `/run/lock/studio1925-install.lock`. Не менять lock и не обходить его. Перед действием повторить те же проверки, записать inode/device/type/mode/owner и baseline службы/health/listeners. Отдельно проверить зависимости аккаунта и совпадение снимка; изменение после аудита = STOP.
3. Создать новые root-owned карантинные каталоги 0700 **на том же filesystem**, что каждый source (например, отдельные закрытые каталоги рядом в /opt, /etc и /var/lib). Назначение должно быть новым и пустым; не использовать существующий путь/ссылку. Перед каждой операцией сверить device/inode исходника и отсутствие destination. Перемещать только весь доказанный source целиком, через same-filesystem rename без перезаписи; никакого copy fallback, glob, rm -rf, chmod -R, переноса Studio/SQLite или автоматического освобождения места. После каждого rename проверить, что исходное имя исчезло, а destination имеет **тот же device/inode**, права и содержимое. Возврат mv --no-clobber сам по себе не доказывает перемещение: он может пропустить существующее назначение.
4. При частичном переносе остановиться, сохранить точную карту уже выполненных rename и закрытый карантин. Не выполнять apply, автоматическое удаление, слепой обратный перенос или restart/reload служб. Любой ручной возврат — только при отсутствии нового source и подтверждении тех же inode/device; иначе отдельный разбор.
5. Аккаунт/group не удалять вместе с home/файлами. Карантин не является основанием удалить identity: повторно проверить отсутствие процессов, чужих файлов, units и групповых зависимостей, отдельно учесть единственные допустимые ссылки в самом карантине. Освобождение dedicated имени без -r — отдельное точно согласованное действие, только если всё доказано; сохранить UID/GID и metadata для восстановления. Если identity нельзя безопасно освободить, apply останется заблокированным — не обходить это.
6. После: исходные TLS имена, owner/checkpoint/runtime/units отсутствуют; карантин закрыт и сохранён; Studio service/listener, локальный и внешний HTTP health, защищённые конфигурации и остальные службы соответствуют baseline. Проверить сохранность SQLite косвенно штатным health; не копировать/восстанавливать базу и не создавать броней. Затем **Manage Studio HTTPS → check**, confirmation пустой. Новое apply — только отдельное разрешение после успешных проверок. Карантин автоматически не удалять.

Весь план исключает firewall, DNS, SSH, VPN/3X-UI/Xray, чужие приложения и их конфигурацию. Действующая Studio и данные SQLite не входят в список карантина. Отчёт не обещает универсально безопасное удаление объектов, которые не удалось проверить.
