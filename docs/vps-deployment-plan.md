# Проект безопасного тестового размещения Studio 19.25 — 2.5.1

**Только проект. На VPS ничего не установлено, не запущено и не опубликовано.** Требуется сначала [аудит двух серверов](vps-audit-runbook.md) и [решение по измерениям](vps-comparison-v2.5.1.md). Существующие VPN, firewall, DNS, 3X-UI/Xray/VPN Manager не изменять. Если на шведском VPS недостаточно безопасного запаса или нужен рискованный перенос VPN, проверяется финский; надёжность SQLite не снижается. Покупки не предусмотрены.

Этот документ уточняет прежний общий [SQLite runbook](sqlite-operations.md): наличие свободных 80/443, домена или нового Nginx **больше не предполагается**. Текущие SERVER/DEMO, пять экранов, изображения, API, бизнес-правила и Pages workflow остаются неизменными.

## 1. Состав и изоляция

```mermaid
flowchart LR
  browser[Mac / телефон] -->|HTTPS, если безопасно согласован| proxy[Изолированный vhost существующего proxy]
  proxy -->|loopback| app[Next.js SERVER / systemd studio1925]
  app --> db[Постоянная SQLite / WAL / FULL]
  app -. контроль .-> health[/api/health]
  db -->|SQLite online backup API| snapshot[Приватный snapshot]
  snapshot -->|зашифрованный restic, периодически| offsite[Уже имеющийся носитель вне VPS]
  vpn[Существующий VPN: конфигурация и службы неизменны]
  ci[GitHub Actions build / тесты] -->|Артефакт после согласования| release[Версионированный релиз]
  release --> app
```

Постоянно работает одно приложение Next.js + SQLite в процессе. Используется существующий безопасный reverse proxy, если он есть; установка нового proxy возможна только отдельным решением после аудита портов. systemd уже входит в Ubuntu; monitoring/backup — короткие oneshot-задачи/timers, без Redis, Docker, БД-сервера, PM2 или постоянно работающего мониторинга.

| Объект | Будущий путь / права |
| --- | --- |
| Системный пользователь | `studio1925`, отдельный group, без sudo, без login shell и членства в VPN-группах |
| Релизы | `/opt/studio1925/releases/<commit>/`, root/deploy владеет кодом; приложение не может его менять |
| Текущий релиз | `/opt/studio1925/current` — атомарно переключаемая ссылка только на код |
| SQLite | `/var/lib/studio1925/studio.sqlite`, каталог 0700 / файл 0600, владелец studio1925; вне checkout/build/public |
| Настройки | `/etc/studio1925/server.env`, root:root 0600; systemd читает файл до смены пользователя |
| Snapshot staging | `/var/backups/studio1925/`, 0700; не внутри релиза и не конечный backup |
| Cache | Только выделенный `.next-server/cache`, доступный приложению; прочий код read-only |
| Node runtime | Проверенная версия Node 24, root-owned, одинаковая с builder; путь фиксируется после аудита |

WAL/SHM также приватны (`UMask=0077`). Файл БД нельзя делать symlink/hardlink или перемещать в public; существующая проверка владельца/прав сохраняется. Environment приложения не содержит backup credentials; они выдаются только backup oneshot. Приложению не передаются VPN-файлы/ключи и переменные их служб.

## 2. Сборка и проверяемый артефакт — без сборки на VPS

**Нового deploy workflow на этом этапе нет.** Ниже спецификация будущей отдельной сборки через GitHub Actions, после согласования. Действующий `demo-pages.yml` не менять и PostgreSQL/SQLite к нему не подключать.

1. Собирать только принятый SHA из main в чистом Ubuntu 24.04 runner соответствующей архитектуры, на закреплённой точной Node 24.x и npm. Архитектуры VPS ещё неизвестны: нельзя отправить x86_64 `better_sqlite3.node` на ARM или собирать на Mac. При отсутствии подходящего бесплатного runner доставку остановить для выбора метода; не запускать тяжёлую сборку на VPN VPS.
2. `npm ci` по lockfile; существующие unit/integration/HTTP/UI, types/lint; `npm run build:server`. Сборка без реальных `.env` и БД. Проверить запуск **готового пакета**, не checkout, с отдельной SQLite и реальным HTTP (создание/конфликт/повтор/health). Контакты только вымышленные.
3. Текущий Next использует `.next-server`, **не standalone**. Для первого простого варианта оставить текущий способ `next start`: allowlist пакета — `.next-server` (без cache), `public`, `package.json`, `package-lock.json`, `next.config.ts`, `src` (без `*.test.ts`), `scripts/database.mjs`, `migrations/sqlite`, Linux `node_modules` из того же lock-based build. Сохранить TypeScript и конфигурационные зависимости: runtime читает `next.config.ts` и `src/lib/app-mode`; CLI импортирует `src/server/*.ts` и `src/lib/*.ts`. Не делать непроверенный `npm prune`/установку на VPS. При упаковке учесть ссылки внутри node_modules, не разрешать выход за release при распаковке.
4. Такой пакет больше оптимизированного standalone: на cloud checkout до этого этапа `du -sh .next-server node_modules public` показал **41M / 727M / 60K**. Это размер данного checkout, **не измерение VPS и не размер будущего tar.gz**. Измерить готовый пакет/распаковку и учесть два релиза. Уменьшение через SERVER-only standalone возможно отдельной проверяемой build-доработкой: tracing не гарантирует включение миграций/CLI/native binary, `public` и static требуют явного копирования. Сейчас Next-конфигурация не меняется.
5. Allowlist исключает `.env*`, `.git`, `out`, тестовые результаты, любые `.sqlite`/WAL/SHM, snapshots, SSH/backup credentials. Для runtime не использовать `.env.sqlite.local`: только явный EnvironmentFile. Проверить перечень файлов, утечки, native ABI и запуск из распакованного архива **без npm install и доступа к БД builder**.
6. Manifest: SHA исходников, OS/arch, точная Node/npm, `process.versions.modules`, SHA256 lockfile, имена/хэши неизменных миграций, Next BUILD_ID, APP_MODE=server, результаты smoke-тестов, размер пакета. SHA256 архива сохраняется отдельно, Actions artifact имеет digest/метаданные run. Архив неизменяемый, named by commit; доставляется именно проверенный артефакт. Повторная установка того же архива воспроизводит релиз. Побайтовая идентичность независимых `next build` **не заявляется** (BUILD_ID/метаданные могут отличаться).
7. Официальные checkout/setup-node/upload-artifact закрепить на проверенные commit SHA, permissions только `contents: read`. Никаких SSH/VPS secrets в build job, production database или автоматического выкладывания на VPS. В public-репозитории обычные Actions бесплатны в рамках правил GitHub; не подключать larger/платные runners. Учитывать срок хранения artifact: согласованный архив и checksum владелец сохраняет вне runner.
8. Владелец получает архив из проверенного run по HTTPS, проверяет SHA256 по **независимо полученному** manifest/digest из принятого run/коммита. Один checksum рядом с подменённым архивом не доказывает подлинность. SSH-доставка с проверкой host key, без `StrictHostKeyChecking=no`. Распаковка только в новый release, без абсолютных путей/`..` и записи в данные/VPN. Повторно проверить hash и владельцев. Старый релиз не удалять.

Это ещё не готовый production-артефакт и не проверка его совместимости с VPS. Его сборка/испытание входят в следующий отдельно согласованный этап, когда известны архитектура и бюджет диска.

## 3. Сеть: дерево решений без покупки домена

Next слушает **только 127.0.0.1:3000**, после проверки, что порт свободен. Если занят — выбрать другой loopback-порт и согласованно задать proxy/health. Не открывать его наружу и не менять firewall на этом этапе.

- Если есть reverse proxy на 443 и владелец подтверждает безопасное добавление отдельного vhost без влияния на VPN, проектируется отдельный HTTPS-hostname и изолированный route. Доступный владельцу бесплатный DNS hostname + бесплатный сертификат Let's Encrypt могут решить задачу без покупки домена. Требуются контроль hostname/DNS, подтверждённый ACME challenge/renewal и разрешённая сетевая схема. Ни free DNS, ни продление ещё не выбраны и не проверены; не обещать URL заранее.
- Если 443 занимает Xray/3X-UI/другой VPN, **не подменять listener, не менять SNI/fallback/stream-routing и не переносить VPN**. Свободный 80 не решает проблему безопасного HTTPS на 443. DNS-01 может получить сертификат, но не освобождает порт. Альтернативный HTTPS-порт также требует согласования открытия и безопасной аутентификации hostname; сейчас не открывается. Проверить Финляндию по тем же правилам.
- Если ни на одном VPS безопасный публичный HTTPS сейчас невозможен, базовый вариант теста с Mac — **существующий SSH-туннель**, без новых публичных listener/портов и без изменений SSH/VPN. Будущая команда после разрешённой установки:

```bash
ssh -N -T -L 127.0.0.1:3000:127.0.0.1:3000 selected-vps
```

В браузере Mac открывается `http://127.0.0.1:3000`; HTTP существует только на loopback, весь удалённый транспорт шифруется SSH. Это **не публичный HTTPS-сайт**, но защищённый тестовый доступ без передачи контактов по открытому интернету. Host key проверяется. `API_PUBLIC_ORIGIN=http://127.0.0.1:3000`, `API_TRUST_PROXY=false`, никаких origin-заголовков от чужого домена. Не делать `-g`/`0.0.0.0`, не публиковать Mac LAN HTTP для телефона.
- Телефон требует собственного доверенного SSH-клиента с local forwarding либо отдельно согласованного HTTPS. Не обещать, что Mac localhost доступен телефону. Установка нового VPN/изменение существующего не является обходным решением. Если бесплатный подходящий клиент/HTTPS не найден, мобильная удалённая приёмка остаётся блокером; screenshots/local E2E не заменяют её.

Бесплатные публичные туннели с промежуточной обработкой контактных данных/случайными URL не подключаются. Локальная CA на телефонах или сертификат на IP требуют отдельного анализа доверия/совместимости и не считаются уже решённой HTTPS-схемой.

### Контракт reverse proxy для будущего HTTPS

Использовать точный `API_PUBLIC_ORIGIN=https://<согласованный-hostname>` и один канонический host, без доверия произвольным Host/X-Forwarded-For. Same-origin POST и отсутствие wildcard CORS сохраняются. См. [контракт API](booking-api-v2.3.md).

- Только proxy принимает интернет; Node — loopback. Если `API_TRUST_PROXY=true`, proxy **заменяет** `X-Studio-Client-IP` своим проверенным адресом peer, не копирует входящий header/XFF. Например, в Nginx без неподтверждённого real_ip: `proxy_set_header X-Studio-Client-IP $remote_addr;`. Сначала проверить, не меняется ли `$remote_addr` чужой real_ip-конфигурацией. Клиент не должен обходить proxy и подделывать этот заголовок.
- До выполнения этих условий `API_TRUST_PROXY=false`; тогда все пользователи разделяют лимиты, это ограничение теста. Настоящая антиспам-защита не возникает автоматически от настройки Origin; non-browser client может её имитировать.
- Лимиты тела/чтения/тайм-аутов и частоты согласовать с API (JSON до 4 KiB); API не кэшировать, не сохранять POST/ответы/тела. У health минимальный ответ, но он проверяет запись в БД: ограничить доступ/частоту независимо, не превращать в публичную диагностику.
- Отдельные access/error logs сайта: не писать имена/телефоны, тело/ответ POST, Authorization, произвольные query строки. Не включать debug/request dumps. Пределы/rotation применяются **только к сайту**, без глобальных изменений журнала/proxy/VPN.
- Любое последующее добавление vhost/сертификата/порта — отдельное согласование, `nginx -t`/аналог и план возврата, с проверкой VPN до/после. Никакого reload/restart proxy в этапе 2.5.1.

## 4. systemd и защита VPN

Будущий unit `studio1925.service` без DependsOn/PartOf/VPN hooks, отдельный пользователь и каталог. Только автоматический restart сайта (`Restart=on-failure`, `RestartSec=5`, ограничение частых стартов). После превышения лимита — сигнал владельцу, а не бесконечная петля. `TimeoutStopSec` проверить на реальной graceful-остановке; backup/migration не прерывать общей командой killall.

Проект параметров, **не готовая команда установки**:

```ini
[Unit]
Description=Studio 19.25 SERVER
After=network.target
StartLimitIntervalSec=60
StartLimitBurst=5

[Service]
Type=simple
User=studio1925
Group=studio1925
WorkingDirectory=/opt/studio1925/current
EnvironmentFile=/etc/studio1925/server.env
Environment=NODE_ENV=production
Environment=APP_MODE=server
Environment=DEPLOY_TARGET=node
Environment=NEXT_TELEMETRY_DISABLED=1
ExecStart=/opt/studio1925/node/bin/node node_modules/next/dist/bin/next start --hostname 127.0.0.1 --port 3000
Restart=on-failure
RestartSec=5
UMask=0077
NoNewPrivileges=true
ProtectHome=true
ProtectSystem=strict
PrivateTmp=true
PrivateDevices=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
CapabilityBoundingSet=
RestrictSUIDSGID=true
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6
ReadWritePaths=/var/lib/studio1925 /opt/studio1925/current/.next-server/cache
MemoryAccounting=true
CPUAccounting=true
IOAccounting=true
CPUWeight=50
IOWeight=50

[Install]
WantedBy=multi-user.target
```

Node path, cache ownership, sandbox compatibility и конечный unit проверяются в следующем этапе, включая offline `systemd-analyze verify`. Не включать `MemoryDenyWriteExecute`: V8 JIT требует совместимости, а не слепого hardening. `PrivateNetwork=true` также не подходит для loopback proxy. Старт напрямую через Node, без npm-wrapper; environment содержит SQLITE_PATH, busy timeout, origin/proxy settings.

**Unit пока неполон для установки:** после аудита добавить `InaccessiblePaths=` со всеми фактическими каталогами VPN, включая нестандартные и world-readable файлы. Нельзя ограничиться предположением `/etc/x-ui`. Список путей владелец проверяет локально; содержимое/секреты не передаёт. `ProtectHome` закрывает `/root`/`/home`; `ProtectSystem` запрещает запись, но сам по себе **не запрещает чтение** VPN в `/etc`/`/usr/local`. Проверить из sandbox отсутствие доступа к контрольным не секретным canary-файлам тех же прав и путей, а не читать реальные ключи. Root-owned код, отдельные uid и отсутствие sudo — обязательны.

CPU/IO weights снижают относительный приоритет только при конкуренции и поддержке cgroups; это не гарантированная изоляция CPU/сети. VPN-unit не меняется. **MemoryHigh/MemoryMax/CPUQuota сейчас не назначаются:** нужны одновременные пики service+backup/VPN и запас. MemoryHigh — ранний сигнал давления; MemoryMax допустим лишь выше измеренного безопасного пика, без системного OOM, с проверкой отказа/восстановления. Если места для такого лимита нет — выбрать другой сервер. Для backup отдельный низкий вес и измеренный memory budget; жёсткий MemoryMax только сайта не защищает от неограниченного backup-процесса.

При росте PSI/swap/OOM, нехватке диска, ухудшении VPN или неясной причинности **первым останавливается сайт/его oneshot-задачи**. Не уменьшать ресурсы VPN, не отключать FULL/WAL, не сжимать лимиты сайта ниже его рабочего профиля. Порог остановки согласовать численно по исходному baseline (минимальная MemAvailable, PSI, CPU load, свободный диск/inode и обычная доступность VPN); до этого shared deployment не разрешать.

## 5. Мониторинг и логи без нового daemon

- systemd контролирует процесс. Отдельный будущий oneshot/timer раз в минуту: `curl --fail --silent --show-error --max-time 5 http://127.0.0.1:3000/api/health`, **только 200** считается здоровьем. Ограниченные повторные проверки; 503 не успех. Проверять также service state, диск/inode, возраст успешного backup. Тайм-аут проверки не равен автоматическому разрушительному восстановлению БД.
- Не выполнять бесконечные перезапуски при full disk/corruption: остановить сайт, сохранить данные, уведомить владельца. Не лечить проблему удалением WAL/DB или автоматическим down-migration.
- Ограничить stdout/stderr service уровнем/частотой systemd; для дискового потолка выбрать отдельный journal namespace сайта с собственным quota/retention или выделенный лог сайта + logrotate. Не менять глобальный journald/retention VPN. Размеры лимитов выбрать из дискового бюджета; проверить суммарные backup/cache/log peaks.
- Никаких контактов, request body, SQL, raw stack или env в logs. Локальный journal также защищён правами, но это не разрешение писать туда персональные данные.
- Внешний наблюдатель — существующий компьютер/NAS владельца либо отдельно согласованный бесплатный scheduled Actions; он нужен для обнаружения полного отказа VPS. Доставка alerts через уже используемые бесплатные GitHub email notifications/почтовый канал после проверки получения. Telegram/новый постоянно работающий мониторинг не внедряются. Schedule GitHub не имеет SLA и может задерживаться; email и резервный контакт пока не выбраны.

## 6. План установки после отдельного согласования

1. Получить оба аудита/историю пиков, подтвердить выбранный сервер, сеть/HTTPS или SSH-туннель, пути запрета доступа к VPN, окно работ и количественные stop thresholds. Проверить обычным подключением владельца, что VPN работает; не проводить нагрузочное тестирование.
2. Подтвердить внешний backup-носитель/ключ восстановления/канал alerts и готовый проверенный CI-артефакт нужной архитектуры. Зафиксировать baseline ресурсов/слушающих портов и состояние VPN без дампа конфигов/ключей.
3. В отдельно разрешённом этапе создать только пользователя/каталоги/настройки/unit сайта, runtime Node при необходимости, новые cache/log/backup timers; проверить firewall остаётся прежним. Не выполнять apt upgrade/перезагрузку VPS/глобальные изменения proxy заодно.
4. Разместить релиз, создать **тестовую** БД отдельным CLI от studio1925, применить существующие миграции 0001/0002, проверить `db:check`; новую миграцию не изобретать. Настроить постоянный путь/права и API origin. Сравнить хэши миграций с manifest.
5. Проверить sandbox, loopback, API/health и права; начать с защищённого ограниченного тестового доступа. Не запускать второй writer из отдельного релиза на той же БД. Проверить application profile и запас VPN; при несоответствии остановить только сайт.
6. Включение выбранного HTTPS маршрута и автозапуска — только по согласованному плану с возможностью возврата. Выполнить тест-план ниже, backup/restore rehearsal, зафиксировать показатели. Службы VPN не перезапускать. Перезагрузка всего VPS — отдельное окно и разрешение, даже для проверки автозапуска сайта.

## 7. Обновление

1. Принятый PR → отдельная build job → неизменяемый артефакт/manifest. Автоматическая доставка без приёмки не включается. Сохранить старый код, текущий manifest и проверенную копию данных.
2. Проверить disk/inode headroom на максимуме старый+новый+архив+snapshot; доставить/проверить/распаковать новый release. Не выполнять npm install/build на VPS и не трогать `/var/lib/studio1925` при очистке кода.
3. Через online backup API получить согласованную контрольную копию и отправить offsite. Для **точного pre-migration checkpoint** остановить только сайт, убедиться, что закончены другие писатели/backup CLI; при необходимости получить ещё один snapshot из закрытой для новых заявок БД. Не обещать нулевую потерю при restore более ранней копии после новых записей.
4. Применить миграции совместимым CLI из нового релиза (Node `--conditions=react-server`, правильный env/SQLITE_PATH, cwd нового release). История/checksums проверяются автоматически. Нет destructive rollback. Миграции — отдельно от старта каждого worker.
5. Атомарно переключить ссылку кода `current`, запустить только studio service; проверить несколько 200 health, минимальные API и пять экранов, baseline VPN и ресурсы. При провале — план отката. Старую версию сохранять до приёмки.

## 8. Backup и восстановление

Сохраняются WAL, FULL, busy_timeout и миграции. **`cp studio.sqlite` работающей БД запрещён**: committed данные могут быть в WAL. Использовать существующий `scripts/database.mjs backup --to <новый-отсутствующий-файл>`: SQLite backup API, integrity/FK-проверка, fsync и атомарное завершение snapshot. [Подробный runbook](sqlite-operations.md).

Будущий timer: короткий oneshot от studio1925, private staging, затем restic с аутентифицированным шифрованием на **уже имеющийся независимый носитель** (Mac/NAS/SSH-storage). Обычная ежедневная копия даёт проектный RPO до суток; для теста уточнить приемлемый RPO/расписание. Носитель должен быть доступен в нужное время; выключенный Mac не обеспечивает успешный ночной backup. Копия на том же VPS не offsite. Без внешнего носителя эксплуатационный критерий не выполнен.

Restic password и SSH-key вне Git/артефактов/приложения; проверка host key. Ключ восстановления хранить отдельно от VPS у владельца. Шифрование не защищает от удаления копий украденными upload credentials: нужны независимое удержание/snapshots/offline-копия на имеющемся носителе. Retention 7 daily / 5 weekly / 6 monthly — только исходное предложение, проверить вместимость. При upload failure staging не удалять, сигнализировать и контролировать его рост. Prune не объединять с каждой записью сайта.

Проверка backup включает exit code, возраст последней успешной копии, `restic check`, периодическое чтение данных и учебное восстановление **в отдельный private путь**. Проверить integrity, applied migration checksums, количество/времена только вымышленных тестовых броней, защиту от пересечений и запуск совместимого релиза на другом loopback-порту. RTO измеряется rehearsal, сейчас не заявлен.

Аварийное восстановление: остановить только studio/timers и все её писатели; сохранить весь исходный каталог БД (main/WAL/SHM), ничего не удалять. Проверить snapshot/offsite и ключ; восстановить через CLI в **новый отсутствующий файл**, с 0700/0600, от правильного uid. Проверить историю/целостность и совместимый код, затем health/API. Возврат старого snapshot может потерять записи после его времени — отдельное решение владельца, без автоматического restore. VPN не участвует.

## 9. Остановка сайта и откат

Будущая точечная процедура, **не выполнялась**:

1. `systemctl stop studio1925.service` и только явно созданные для сайта health/backup timers. Дождаться завершения уже запущенного SQLite backup/migration; не убивать процессы по общему имени `node`/`xray`, не использовать reboot/killall.
2. Если проблема в коде, а текущая схема совместима со старым релизом, атомарно вернуть `current`, запустить **только** studio и проверить health/VPN. Файл БД не откатывается вместе с кодом.
3. При несовместимой схеме или повреждении — сайт остаётся остановленным, offline-план восстановления выше и решение по возможной потере записей. Автоматически запускать старый код поверх неизвестной схемы нельзя.
4. Если риск для VPN сохраняется, сайт остаётся остановленным. Удалять/отключать только его согласованный vhost/unit, без restart VPN/изменения 443 listener. Возврат proxy-конфига — отдельный проверенный change владельца, если его вообще меняли.
5. Сверить VPN с исходным состоянием обычным клиентским подключением и техническими показателями, зафиксировать результат. Не откатывать системные файлы/маршруты/конфиги VPN из «общего backup сайта».

## 10. Будущая приёмка (только вымышленные контакты)

| № | Сценарий | Доказательство / условие остановки |
| --- | --- | --- |
| 1 | VPN до установки | Обычное подключение владельца и baseline; если плохо — работы не начинать |
| 2 | Независимый запуск Studio | Отдельный uid/unit, loopback, нет DependsOn/PartOf VPN; проверка sandbox/canary |
| 3 | Защищённый адрес | Доверенный сертификат/HTTPS на Mac и телефоне, renewal; либо отдельно принятый SSH-only тест, который не закрывает публичный HTTPS критерий |
| 4 | Все пять экранов | Welcome → Calendar → Time → Contacts → Confirmation; моб./desktop, корректный SERVER |
| 5 | Запись в SQLite | Подтверждение только после 201; бронь видна в availability после reload, без контактов в GET/logs |
| 6 | Конфликт / соседство | Два клиента на один ресурс/интервал → одна бронь, второй 409; соседние интервалы допустимы |
| 7 | Перезапуск сайта | Перезапустить только studio, сохранённая бронь остаётся; VPN работает |
| 8 | Автозапуск после reboot VPS | **Отдельное окно и разрешение владельца**, проверка VPN/Studio после штатной перезагрузки; иначе тест помечается невыполненным |
| 9 | Отказ приложения | Контролируемый отказ только studio, restart/ограниченный retry/alert, VPN остаётся доступным |
| 10 | Откат сайта | Старый совместимый релиз, та же БД, VPN/порты неизменны |
| 11 | Backup / restore | Online snapshot + зашифрованный offsite + восстановление в отдельный путь, integrity/бронь/измеренное RTO |
| 12 | VPN после всех проверок | Обычное подключение, baseline ресурсы/порты/services, нет ухудшения; иначе stop сайта |

Дополнительно проверить 503 и восстановление при временно недоступном **тестовом** каталоге БД, ошибки записи без удаления main/WAL; не заполнять диск и не вызывать OOM на live VPN VPS. Сетевой сбой/потеря ответа повторяется с тем же UUID; контакты не сохраняются в browser storage. Нельзя проводить отказные/нагрузочные тесты VPN.

## Необходимые будущие изменения и открытые вопросы

Изменения только на выбранном VPS и только после согласования: пользователь/каталоги/права, runtime Node при необходимости, код-артефакт, тестовая SQLite/init/migrate, unit сайта и его sandbox, health/backup timers, изолированные logs/rotation; reverse proxy/vhost/сертификат **если безопасно разрешены**. По умолчанию firewall/VPN/DNS/порты не меняются. Точный diff ещё невозможен без аудита.

Блокеры: факты двух VPS и пики VPN; OS/arch/Node/место; владельцы 80/443 и TLS; безопасный HTTPS/Mac+телефон или принятый tunnel-only доступ; внешний backup-носитель и recovery key; alert channel; количественные resource thresholds; перечень VPN-путей для sandbox; maintenance/reboot window; измерение и smoke-тест готового артефакта. До решения этих вопросов сервер не выбирается, установка не начинается. Правовые условия реальных контактных данных отдельно не решены; этап использует только вымышленные данные.
