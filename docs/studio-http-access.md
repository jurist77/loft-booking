# Enable Studio HTTP access

Ручной workflow для технического доступа к Studio по TCP/3000. Он не входит в
установку/обновление и не запускается по push, расписанию или завершению другого
workflow. Ветка выполнения — только `main`. До отдельной приёмки PR и разрешения
владельца запускать его на VPS не следует.

HTTP допускается только для тестов с вымышленными контактами. До работы с реальными
данными нужен HTTPS. Этот workflow HTTPS не настраивает.

## Запуск после согласования

1. Откройте GitHub → Actions → **Enable Studio HTTP access** → Run workflow.
2. Выберите `main`, введите буквальный IPv4 или IPv6 в `server_ip` (без URL, порта,
   квадратных скобок и имени узла). IP не хранится в исходном коде.
3. Сначала оставьте `mode=check`. Поле `confirmation` пустое.
4. Прочитайте Summary, включая `reason`, `observations` и `external_before`.
5. Только после отдельного решения владельца выберите `apply` и введите строго
   `ENABLE STUDIO TCP 3000`. Пробел в конце тоже делает подтверждение неверным.
   Workflow заново выполняет проверку, а не доверяет результату прошлого запуска.
6. Прочитайте итог. Зелёное наличие правила само по себе не доказывает внешний доступ.

Используется существующий `STUDIO_SSH_PASSWORD`: пароль root, SSH порт 22. Новых
Secrets не нужно. Пароль передаётся `sshpass -e` через окружение SSH-процесса, без
аргументов, постоянных файлов и артефактов. Исходники удалённой операции передаются
через приватный временный файловый поток runner, совместимый с `Popen(stdin=...)`.

Согласованная политика Studio отключает проверку host key только опциями отдельного
SSH-вызова (`-F /dev/null`, known-hosts `/dev/null`). Это риск MITM: подставной сервер
может получить root-пароль и подделать отчёт. Очищенный JSON не устраняет этот риск.
Глобальные SSH-настройки runner/VPS не меняются.

## Что проверяется

- SSH/root и существующая штатная блокировка `/run/ufw.lock`.
- Загруженная, активная, работающая `studio1925.service`; MainPID не публикуется.
- Полное наблюдение `ss -H -O -4/-6 -lntpe sport = :3000` обоих семейств (`-O` — одна
  строка на сокет). Все владельцы
  TCP/3000 должны совпадать с MainPID Studio; каждый fd дополнительно сверяется
  через read-only `/proc/MainPID/fd/N` с inode сокета. Нужны native wildcard bind
  семейства введённого IP либо доказанный IPv4 dual-stack по правилам ниже и
  успешный локальный health. Чужой процесс, ограниченный bind и неизвестное
  владение не исправляются открытием firewall.
- UFW active, входящая политика deny, IPv6 включён, `MANAGE_BUILTINS=no`.
- Полные `iptables-save`/`ip6tables-save`, альтернативное legacy-представление и
  native `nft -j list ruleset`. Поддерживаются согласованные nft или legacy backend;
  фильтрация в другом backend, NAT/mangle/raw-правила, сторонние цепочки, дополнительные
  hooks, sets/maps и неизвестные конструкции приводят к отказу. Даже цепочка,
  кажущаяся неиспользуемой, не считается разрешением менять сложный firewall.
- Для нового внешнего TCP/3000 к локальному unicast-адресу проверяются все возможные
  ветви неизвестных условий: до добавления — DROP, после виртуального append в
  UFW user-input — ACCEPT. Оба семейства и оба применимых представления должны
  согласоваться. Неизвестный путь никогда не даёт `READY_TO_APPLY`.
- Сохранённые UFW rules должны совпадать с активными. Поддерживаются простые
  числовые TCP/UDP allow-правила других портов. Существующие правила 3000, ranges,
  application profiles, wildcard tuples, противоречия и legacy RETURN в user-цепочках
  требуют ручного разбора. Существующее разрешение не заменяется новым.
- С runner выполняется ограниченный GET `http://IP:3000/api/health`, без редиректов
  и контактных данных. Ожидается именно HTTP 200 и `{"status":"ok"}`.

`READY_TO_APPLY` относится к поддержанному **локальному netfilter/UFW-пути**, а не
ко всей сети. Firewall провайдера, NAT вне VPS и маршрут runner не контролируются.
Данные предыдущей диагностики сервера с дополнительными цепочками не являются
предварительным разрешением: такой сервер может получить `BLOCKED_FOR_SAFETY`.
Не удаляйте цепочки VPN и не переключайте backend ради прохождения этой проверки.

### IPv4 через IPv6 wildcard

Отсутствие отдельной строки `0.0.0.0:3000` не доказывает отсутствие IPv4 listener:
один IPv6 сокет на `::` может принимать IPv4-mapped подключения. Для этого конкретный
сокет должен иметь `IPV6_V6ONLY=0`. Расширенный `ss -e` выводит `v6only:0` из
kernel-атрибута `INET_DIAG_SKV6ONLY` именно этого сокета. Глобальный
`net.ipv6.bindv6only` не используется: приложение могло переопределить его при
создании listener. Отсутствующее поле не интерпретируется как ноль.

Для IPv4 fallback одновременно обязательны:

1. Ровно один TCP/3000 listener во всех наблюдениях IPv4 и IPv6: IPv6 wildcard
   `::` (или `*` в выводе `ss -6`), без scoped address и с явным `v6only:0`.
2. Ненулевые inode/cookie, полный список владельцев только MainPID Studio и
   подтверждённое соответствие fd → `socket:[inode]`.
3. Успешные локальные HTTP health и по `127.0.0.1`, и по `::1`.
4. До и после health одинаковые PID/состояние службы, inode, cookie, fd, адрес,
   опция и подтверждение владения. Замена даёт `LISTENER_STATE_CHANGED`.

Отдельный IPv4 loopback listener, несколько IPv6/reuseport сокетов, неизвестная
опция, `v6only:1`, скрытые/чужие владельцы или недоступные fd не позволяют угадать
dual-stack по двум HTTP 200. Такой IPv4 fallback блокируется. Для native IPv4
wildcard и native IPv6 wildcard сохраняется прямое доказательство, с той же
проверкой владения. Поддержка более сложных множественных dual-stack listeners
требует отдельного доказательства, а не снятия проверки.

`observations.bind_proof`: `native_ipv4`, `native_ipv6`, `ipv4_dual_stack` либо
`unconfirmed`. PID/fd/inode/cookie и targets из `/proc` в отчёт не передаются.
Identity и per-socket option включены в отпечаток preflight/apply, поэтому новый
сокет с тем же PID/адресом не наследует прежнее разрешение. После добавления UFW
правила bind/владение/health проверяются повторно. Проверка остаётся наблюдением,
а не заморозкой процесса: неконтролируемые изменения после снимка не исключены.

Успешный bind guard **не** возвращает `READY_TO_APPLY` сам по себе. При недоступном
внешнем health продолжаются все проверки UFW, active/persisted rules, обоих
netfilter backend и native nft hooks. Их неоднозначность по-прежнему блокирует
изменение. Уже подтверждённый внешний доступ сохраняет прежний результат
`ALREADY_ACCESSIBLE`/`NO_CHANGE_REQUIRED` без изменения firewall.

## Почему не просто `ufw allow`

Аудированный исходник Ubuntu 24.04 `ufw_0.36.2-6_all.deb` имеет SHA256
`096eb403ecaf6740d160bb306970f025222ef71324319cc1cb78d06dfa462ef1`.
Источник: [официальный архив Ubuntu](https://archive.ubuntu.com/ubuntu/pool/main/u/ufw/).
Это бесплатное ПО Canonical под GPL; его исходники в репозиторий не копируются.

В UFW 0.36.2 `initcaps()` обычно создаёт/удаляет тестовые цепочки;
`set_rule()` при замене правила или нехватке цепочек может перезагрузить user chains.
Поэтому обычный CLI без дополнительных ограничений не подходит этому заданию.

Реализация проверяет SHA256 CLI и всех восьми Python-модулей установленного UFW,
root-владение и отсутствие записи для группы/прочих у читаемых файлов. На другой
версии или изменённом исходнике — отказ. **Установщик ничего не переустанавливает
и не предлагает downgrade UFW.** Для иной версии нужен отдельный аудит и тесты.

Под уже удерживаемой штатной POSIX-блокировкой UFW выполняется его проверенный CLI
в том же Python-процессе, с фиксированными аргументами:

```text
ufw allow in proto tcp from any to any port 3000
```

Один UFW allow генерирует **два** узких kernel-правила: IPv4 и IPv6, TCP/3000.
Другие порты не открываются. Для каждого семейства обязательны существующие
input/output/forward/limit/limit-accept цепочки.

Только в памяти этого короткого процесса:

- повторный захват уже удерживаемой блокировки CLI подавляется;
- capabilities берутся из проверенного существования limit-цепочек, без временных
  тестовых chains; выбранное allow не использует recent/limit;
- reload/pipeline запрещены, попытка удаления устаревшего RETURN подавляется
  (его отсутствие проверено заранее);
- subprocess boundary разрешает только ограниченные чтения и точный append
  TCP/3000 в соответствующую user-input цепочку;
- сначала настоящий сериализатор UFW выполняется с перенаправлением всей файловой
  записи в память и симулированным append. Обе будущие конфигурации должны отличаться
  ровно одним новым tuple/правилом каждая. Лишь затем разрешается реальное добавление.

Изменения Python-функций не сохраняются в UFW/SSH/config-файлах. `check` не создаёт
файлов на VPS и не выполняет kernel append. Блокировка требует уже существующего
root-owned файла; при его отсутствии/занятости проверка прекращается.

Перед apply заново проверяется отпечаток состояния из preflight. Из него исключены
volatile counters, handles и очереди сокетов. После apply сравниваются все таблицы,
правила, порядок внутри цепочек, политики и значимые UFW-файлы. Допускается только
указанное добавление. Затем проверяются UFW allow, служба, локальный health и
независимый внешний health с runner.

Обычные UFW-команды сериализуются этой блокировкой. Прямые изменения firewall другим
администратором/ПО её могут обходить. Это не атомарная транзакция firewall: два семейства
и файлы меняются последовательно; сбой процесса/диска может оставить частичное состояние.
Любое изменение firewall потенциально влияет на существующие соединения. Абсолютное
отсутствие влияния на VPN не гарантируется; в окно изменения не следует параллельно
администрировать сеть. Check тоже кратковременно удерживает блокировку UFW.

## Результаты

| Режим | Статус | Значение |
| --- | --- | --- |
| check | READY_TO_APPLY | Поддержанный локальный путь и точный append доказаны; изменений нет |
| check | ALREADY_ACCESSIBLE | Внешний health и принадлежность listener Studio подтверждены |
| check | BLOCKED_FOR_SAFETY | Конфликт/неподдержанная фильтрация или состояние Studio |
| check | INCONCLUSIVE | Неполные чтения, неизвестный путь/версия UFW, SSH/lock недоступен |
| apply | SUCCESS | Точный delta, локальный и внешний health подтверждены |
| apply | NO_CHANGE_REQUIRED | Доступ уже подтверждён; правило не добавлялось |
| apply | FAILED_NO_CHANGE | Отказ до начала изменения, включая неверное подтверждение |
| apply | APPLIED_BUT_UNREACHABLE | Точный allow добавлен, локальные проверки прошли, внешний health не подтверждён |
| apply | MANUAL_REVIEW_REQUIRED | Возможно частичное изменение или потерян ответ; требуется проверка владельца |

`change_possible=true` означает возможность изменения; при `MANUAL_REVIEW_REQUIRED`
это **не** подтверждение успешно добавленного правила. `observations` относится к
preflight. `postflight` появляется только после полного локального сравнения delta;
`external_before` и `external_after` различают две внешние проверки. Промежуточный
`APPLIED_PENDING_EXTERNAL` используется только между SSH и runner, не является SUCCESS.
При отказе шаг красный; готовый отчёт сам по себе не доказывает устранение проблемы.

Автоматического отката/удаления нет. При неопределённом состоянии сохраните очищенный
Summary и передайте владельцу для ручного разбора. Не выполняйте вслепую повторные
изменения, UFW disable/reload или удаление чужих правил. Существующий allow плюс
внешний timeout блокирует повторное добавление; требуется диагностика другого слоя.

В логах нет raw ruleset, комментариев/адресов из правил, содержимого UFW-файлов,
журналов служб, PID, HTTP bodies, пароля или traceback. Артефакты не создаются.
Обнаружение правильного IP/адреса без проверки host key остаётся ответственностью владельца.

## Изолированные тесты

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests/firewall -v
```

Три файла feature-логики разделяют runner/SSH, read-only доказательство пути и
строго ограниченную host-операцию. Тесты используют stateful fixtures и перехватывают
все subprocess-вызовы настоящего UFW. Проверяются подтверждение, оба режима, права
на изменение, отсутствие дубликатов, чужие процессы, bind, UFW inactive, deny/range/
scoped rules, альтернативные backend/hooks, несоответствие сохранённых правил,
гонка preflight/apply, ошибки добавления, потеря SSH-ответа и внешний timeout.

Отдельный **Check Studio HTTP access** запускается на x64 и ARM64. Он извлекает
вышеуказанный `.deb` как тестовые данные после SHA256-проверки, **не устанавливает**
его и не вызывает реальный firewall. `STUDIO_UFW_TEST_SOURCE` задаётся только для
изолированных тестов, не читается production workflow. Без него пять тестов
настоящего UFW помечаются skipped, а не выдают ложный pass. Пакет можно извлечь
в локальный временный каталог аналогичными командами из CI и задать эту переменную.

Тесты не доказывают доступность конкретного VPS. Приёмка владельцем после merge:
check → отдельное решение об apply → внешний и локальный health → проверка VPN
и другого приложения их обычным пользовательским способом. К реальному серверу
при разработке не подключались; настоящие check/apply не выполнялись.
