# Восстановление health после перезапуска PostgreSQL

Основание: `main` на `cb0b8b1c26ab9a152587f32f88bda5d93431acf4`, после merge PR №5. Проблемный запуск: [39159260480](https://github.com/jurist77/loft-booking/actions/runs/39159260480). Исправление готовится в `fix/backend-health-recovery-ci`, без merge и без этапа 2.2.

## Диагноз

В старом HTTP-тесте `spawnSync` выполнял Docker Compose в том же процессе, который использовал глобальный `fetch`/Undici. Во время синхронной команды обработка HTTP-событий и таймеров клиента останавливалась. Next.js при этом продолжал работать и мог закрыть простаивающее keep-alive соединение. Сразу после Compose клиент мог повторно использовать старый сокет до обработки его закрытия. Результат — `TypeError: fetch failed`, `UND_ERR_SOCKET: other side closed`, вместо нового HTTP-ответа.

Это воспроизведено **на настоящем Next.js и PostgreSQL**, без подмены запросов:

- Node.js **24.12.0 / Undici 7.16.0**: после синхронного `compose up` длительностью около 5,8 секунды диагностический канал `undici:client:sendHeaders` показал повторную отправку через ранее использованный socket 1; запрос завершился `UND_ERR_SOCKET`. Процесс приложения оставался жив. Новый `node:http` запрос получил `{"status":"ok"}` от того же приложения сразу после ошибки.
- Повторные испытания старого клиента также воспроизвели ту же ошибку на проверке 503 после остановки: транспортная гонка не ограничена единственным переходом.
- Node.js **24.19.0 / Undici 7.29.0**: пять обычных циклов и дополнительная контролируемая синхронная пауза не воспроизвели ошибку; клиент создавал новое соединение. Следовательно, проявление зависит от версии HTTP-клиента и времени завершения Compose. Само окружение GitHub Actions не требуется для воспроизведения.

Отдельно проверены пул `pg` и процесс Next.js: в исправленном тесте **один и тот же процесс и его существующий пул** проходят несколько остановок/восстановлений подряд. Код пула, health endpoint и подключения не изменён. Обновление health через новый сокет показывает, что ошибка старого HTTP-клиента не доказывала отказ БД или падение Next.js.

Полный архив старого CI-лога недоступен в текущей облачной среде из-за ограничения доступа к `results-receiver.actions.githubusercontent.com`. Метаданные GitHub подтверждают, что упал только HTTP-шаг после успешных build/integration. Указанная выше patch-версия Node — версия **локального воспроизведения**, не утверждение о точной версии старого runner. Новый тест выводит Node/Undici в журнал, чтобы последующая диагностика не зависела от догадок. Официальный архив Node 24.12.0 использовался из `/tmp` после проверки SHA-256 по официальному SHASUMS256; зависимости и версия Node проекта не менялись.

## Исправление

- `scripts/lib/health-probe.mjs`: настоящие `node:http` запросы с `agent: false` и `Connection: close`. Каждый запрос имеет новый сокет; глобальный fetch pool не участвует.
- `scripts/verify-server.mjs`: асинхронный Compose для **тестового** project; три последовательных цикла `200 → 503 → 200`. Мониторится непосредственно PID Next.js, без промежуточного npm/wrapper. Во время циклов Next.js не перезапускается.
- После healthy Compose разрешено не более **15 секунд** ожидания HTTP 200, с интервалом до 200 мс и ограничением отдельного запроса до 3 секунд. Общая граница учитывает и время запросов. `503` после восстановления не считается успехом.
- Неожиданные статусы (включая 404/500), неверные body/cache headers завершают проверку сразу. Повторяются только временные сетевые отказы и корректные ответы 200/503, ещё не соответствующие ожидаемой фазе. Завершение процесса приложения прекращает ожидание.
- Диагностика выводит фазу, число попыток, последний безопасный код/HTTP-статус, время, версию Node и состояние процесса; без сырых исключений, URL, SQL, содержимого ответов и секретов. Последние миллисекунды общего бюджета не расходуются на заведомо обречённый микрозапрос, который затёр бы реальный HTTP-статус искусственным abort.
- `finally` восстанавливает остановленную тестовую БД и завершает Next.js даже при ошибке. Остановка приложения ограничена по времени: SIGTERM, затем SIGKILL при необходимости. Volume не удаляется.
- `scripts/verify-health-failure.mjs`, npm script `test:server:http:failure`: отдельный CLI намеренно оставляет БД выключенной, требует 200, получает устойчивый 503 и **реально завершается с exit 1**. Родительская отрицательная проверка принимает только этот ожидаемый timeout, живой Next.js и подтверждённую очистку; произвольное падение не засчитывается.
- `.github/workflows/backend-checks.yml`: отрицательная проверка добавлена после положительных циклов. Существующий workflow Pages не изменён.

## Повторение проверки

В корне проекта, после установки Node 24/Docker:

```bash
npm ci
npm run db:env
npm run db:test:up
npm run build:server
npm run test:server:http
npm run test:server:http:failure
```

Обычная команда проверяет три цикла; отрицательная — отдельную команду, завершившуюся с кодом 1 при постоянном отказе. Если нужно увидеть этот код непосредственно:

```bash
node scripts/verify-server.mjs --keep-db-stopped
```

Это **намеренно неуспешный тест**: ожидается `HEALTH_TIMEOUT ... expected=200 ... last=HTTP_503`, затем восстановление БД, остановка Next.js и exit 1. Не использовать его вместо обычной положительной проверки. Порт 3011 должен быть свободен; запуск при занятом порте не затрагивает БД. Настоящие контакты/производственные настройки не нужны.

## Границы и оставшиеся риски

Предел восстановления 15 секунд намеренно конечный: более медленное или постоянное восстановление даёт ошибку CI. Этот тест не моделирует нагрузку, failover или промышленную отказоустойчивость PostgreSQL. Конкретная patch-версия старого GitHub runner пока не установлена из полного архива; новую версию теста можно проверять по явному runtime-сообщению.

Приложение, пул БД, миграции/таблицы, дизайн, пять экранов, правила времени, фотографии/логотип, AGENTS.md и `.github/workflows/demo-pages.yml` не меняются. Публичный адрес DEMO сохранён. VPS и этап 2.2 не начаты.
