# studio 19.25: один Next.js и SQLite

## Аудит и решение

Основание — `main` **17851598865ec8f3aa4c835d5965a36a2d5c4349**. PR №5 (PostgreSQL foundation) и PR №6 (health recovery CI) объединены, открытых PR на начало работы нет. Новая ветка — `feat/sqlite-backend-simplification`. Пятиэкранный интерфейс и Pages workflow не меняются.

| Свойство | PostgreSQL foundation | SQLite в этой ветке |
|---|---|---|
| Надёжность | Отдельный зрелый сервер, транзакции; нужны его готовность, роли и соединения | Зрелый SQLite 3.53.4 через better-sqlite3 13.0.3; WAL/FULL, транзакции и SQL-триггеры; зависит от локального диска |
| Эксплуатация | Next + PostgreSQL, Docker/volume, порты, роли, пароли, пул | Next + локальный файл, без DB daemon/порта/паролей/Compose |
| Конкурентность | Много параллельных писателей, развитые серверные блокировки | Один писатель; короткие транзакции и busy_timeout. Достаточно для одной небольшой студии |
| Резервирование | pg_dump/серверные инструменты и отдельный процесс | Online backup API снимает согласованный snapshot, включая WAL; затем restic шифрует/выносит его |
| Восстановление | Восстановить сервер/роли/дамп и приложение | Остановить Next, сохранить повреждённый каталог, восстановить проверенный snapshot в новый файл, проверить и запустить |
| Основной риск | Больше эксплуатационных настроек и отказов отдельных компонентов | Сбой/заполнение диска VPS; потеря VPS без независимой внешней копии; длительная запись блокирует других писателей |

Для одного VPS и одной студии выбран SQLite без дополнительных очередей, сервисов блокировок, ORM и внешних БД. Целевая схема: **HTTPS reverse proxy → один Next.js Node → локальный SQLite**. systemd обеспечивает запуск/перезапуск и периодические задачи; PostgreSQL удалён из активных зависимостей и CI. Текущие PostgreSQL volumes и env не удаляются, данных из них автоматически не переносим: прежний backend содержал только журнал, не реальные бронирования. История Git и исходный SQL сохранены.

## Режимы и компоненты

- `APP_MODE=demo`: прежний интерфейс/вымышленные данные, без SQLite, отправки/хранения контактов. GitHub Pages остаётся https://jurist77.github.io/loft-booking/.
- `APP_MODE=server`: Next.js Node, настоящий `/api/health`, SQLite. Запись в интерфейсе пока отключена; demo fixtures не выдаются за настоящую занятость.
- `src/server/config.ts`: явный режим, абсолютный SQLITE_PATH вне checkout, bounded timeout. Наличие файла или переменной не включает SERVER.
- `src/server/database.ts`: одна переиспользуемая SQLite connection на процесс; открытие только существующего файла, WAL, synchronous=FULL, foreign_keys=ON, trusted_schema=OFF; busy timeout 1000 мс (50–5000). Закрытие для скриптов/тестов.
- `src/server/migrations.ts`: SQL-версии, SHA-256, BEGIN IMMEDIATE и атомарный пакет SQL/истории.
- `src/server/backup.ts`: native online backup + integrity check, временный private-файл, fsync и атомарная публикация без перезаписи.
- Все серверные модули `server-only`. `route.server.ts` по-прежнему включается только в SERVER через pageExtensions. В DEMO нет API и native-модуля в браузере.

`better-sqlite3` — зрелая бесплатная MIT-библиотека, поддерживаемая Next.js как server-external dependency. Node 24 LTS выбран для CLI и приложения. На другой ОС/архитектуре native-модуль переустанавливается через npm ci. Нельзя переносить node_modules с Mac на Ubuntu.

## Файлы и доступ

База — например `/var/lib/studio1925/studio.sqlite`, **вне релизов, build и public**. Каталог принадлежит пользователю приложения и имеет 0700, файл и WAL/SHM — 0600. Symlink/hardlink и открытые групповые/общие права отклоняются; приложение не исправляет чужие права молча. Runtime не создаёт каталог/пустую замену при пропаже базы. Создание — отдельная команда init.

Перед повторным использованием connection проверяются путь, права и inode. Если файл исчез, недоступен или восстановлен другим inode, соединение закрывается; после восстановления путь открывается заново. Это предотвращает ложную работу через старый открытый FD. База должна находиться на **локальной файловой системе**, не NFS/SMB/cloud-synced каталоге. WAL не даёт безопасной общей БД для нескольких VPS.

Ошибки пути/диска/SQLite наружу не выводятся. `.env.sqlite.local`, базы/копии/WAL/SHM и локальные данные игнорируются Git. DB-путь приватный, не NEXT_PUBLIC. Старые PostgreSQL env остаются игнорируемыми до ручной очистки владельцем и не используются как fallback.

## Схема и защита интервалов

Первая SQLite-миграция создаёт `schema_migrations` (runner), одну строку `_health` для проверки записи и **минимальную** `bookings`: id, starts_at/ends_at (UTC epoch milliseconds), confirmed/cancelled. Контактов, событий, идемпотентности и API пока нет. Это SQL-основа, а не реализация клиентской записи.

CHECK ограничивает минимум 60 минут, шаг 30 минут и рабочий день 09:00–23:00. Московские часы в SQL проверяются с текущим UTC+3; существующие расчёты UI остаются Europe/Moscow. Если законодательство изменит зону, SQL-ограничения потребуется мигрировать. Будущий API обязан повторять текущие проверки времени/окна +3 месяца по серверным часам; динамическое окно и запрет прошлого не заменяются статическими CHECK.

INSERT/UPDATE триггеры отклоняют пересечения активных полуоткрытых интервалов `[start,end)` с `BOOKING_OVERLAP`. Соседние разрешены, cancelled не блокируют время; возврат cancelled в confirmed также проверяется. SQLite блокирует писателей до проверки/записи, поэтому два независимых процесса не могут одновременно зафиксировать один интервал. Будущая операция с несколькими SQL-изменениями должна использовать одну короткую BEGIN IMMEDIATE транзакцию; отдельный предварительный SELECT не обеспечивает защиту.

Серверные операции бронирования, API, реальная занятость и админ-панель **не реализованы**. Схема пока не является полным контрактом хранения персональных данных. Модель контактов/идемпотентности и правовые требования потребуют отдельного согласованного этапа.

## Миграции

Активные файлы — `migrations/sqlite/0001_*.sql` и далее без пропусков. PostgreSQL SQL сохранён в `docs/archive/postgresql/`, не исполняется SQLite. Это отдельная история нового движка; импорт production-данных не заявляется.

Файлы после применения неизменяемы. Runner проверяет весь применённый префикс (версия/имя/SHA-256) перед pending SQL. BEGIN IMMEDIATE сериализует миграторы; busy timeout даёт ненулевой MIGRATION_LOCKED. SQL-ошибка откатывает весь pending пакет и историю, повтор применяет ноль версий. HISTORY_MISMATCH останавливает выполнение. Автоматического down/удаления данных нет. Файлы — reviewed SQL, без собственных BEGIN/COMMIT/ROLLBACK. SQLite не разделяет SQL-роли: доступ контролирует пользователь ОС; приложение/администратор с доступом к файлу технически могут изменить всё.

## Health, отказы, CI

Health проверяет quick_check/foreign keys и маленькую **committed write** в `_health`. SELECT 1 не заметил бы readonly/full. Норма — 200 `{"status":"ok"}`, ошибка — 503 `{"status":"unavailable"}`, Cache-Control no-store. Подробности/SQL/путь не раскрываются. При исправлении доступа соединение открывается снова; отсутствующая БД не заменяется пустой. Это не инструкция автоматически чинить повреждённый файл: требуется проверенная копия.

PR №6 сохранён по смыслу: отдельные HTTP-сокеты, ограниченное ожидание, контроль реального PID и finally-cleanup. Тестовая SQLite хранится только в собственном temp-каталоге. Три настоящих цикла 200→503→200, readonly→503→200 и отдельный отрицательный CLI с exit 1 проверяют восстановление и постоянный отказ. Пул PostgreSQL/Compose исчезли; health-probe из PR №6 сохранён без ослабления.

Backend CI больше не требует Docker, production DB или VPS. Pages workflow оставлен байтово прежним. Static DEMO строится с недоступным SQLite path и canary, аудит отвергает DB/API/native server-код/приватный путь в out/.

## Копирование и эксплуатация

Live snapshot делается только SQLite backup API. Прямое копирование одного основного файла при WAL небезопасно. Backup включает committed WAL, проверяет integrity/foreign keys и публикует новый private-файл. При непрерывных внешних записях SQLite может перезапускать копирование; progress ограничен общим бюджетом 60 секунд и завершается ошибкой, не выдаёт неполную копию за готовую. Это локальный snapshot: шифрование/хранение вне VPS выполняет будущая oneshot restic-задача.

Восстановление пишет только в **новый отсутствующий файл**, никогда поверх живой базы. Production restore выполняется offline с сохранением всего прежнего каталога. Подробнее: [локальная инструкция](backend-local-setup.md), [VPS/backup/recovery runbook](sqlite-operations.md), [отчёт проверки](sqlite-acceptance.md). VPS, HTTPS, внешнее backup-хранилище и уведомления сейчас только спроектированы, не подключены.

## Зафиксированные продуктовые правила для следующих этапов

1. Одна студия — studio 19.25.
2. Рабочие часы 09:00–23:00.
3. Часовой пояс Europe/Moscow.
4. Шаг 30 минут.
5. Минимум 60 минут.
6. Максимум ограничен одним рабочим днём, до 14 часов; выход за его границы запрещён.
7. Буфера между бронями нет.
8. Соседние `[start,end)` интервалы разрешены.
9. Реальное бронирование автоматически подтверждается после успешной записи в БД.
10. Лимита количества броней на один телефон пока нет.
11. Повтор того же запроса должен быть идемпотентен; самостоятельное новое бронирование разрешено.
12. Клиент не изменяет/отменяет бронь самостоятельно.
13. Отменённые брони сохраняются в истории, освобождая интервал.
14. Окно — московская текущая дата +3 календарных месяца включительно с прежним clamp короткого месяца.
15. Контакты — имя, фамилия, российский мобильный телефон.
16. Оплаты на этом этапе нет.

Эти правила сохранены; SQL-основа реализует только ограничения интервалов. Серверных клиентских операций записи пока нет.
