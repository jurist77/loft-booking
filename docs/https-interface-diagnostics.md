# CHECK_INTERFACES: iproute2 JSON, прямой IP и границы NAT

## Установленные факты

[Run 42618625409](https://github.com/jurist77/loft-booking/actions/runs/42618625409) прошёл чтение интерфейсов и остановился после `CHECK_INTERFACES` с `HTTPS_OPERATION_FAILED`.

В прежнем коде отсутствие ожидаемого публичного IP на корректно разобранных интерфейсах давало отдельный `DIRECT_PUBLIC_ADDRESSES_REQUIRED_NO_NAT_ADOPTION`. Ошибка чтения команды остановила бы проверку раньше, на `READ_INTERFACES / PREFLIGHT_READ_INCOMPLETE`. Поэтому **общий сбой этого запуска не доказывает ни NAT, ни отсутствие публичного IP**: он относится к разбору данных перед проверкой принадлежности IP.

Найден и воспроизведён конкретный дефект: `ip -j address show scope global` может выдавать пустые `{}` внутри `addr_info`. iproute2 открывает JSON-объект в `print_selected_addrinfo`, затем `print_addrinfo` может выйти из-за фильтра scope, ничего не записав внутрь. Источник: [создание объекта](https://github.com/iproute2/iproute2/blob/v6.1.0/ip/ipaddress.c#L1739), [scope filter](https://github.com/iproute2/iproute2/blob/v6.1.0/ip/ipaddress.c#L1557).

Такие объекты наблюдались при локальном read-only запуске штатного iproute2 6.15.0. Старый цикл на этом же ответе воспроизводит `KeyError('local')`. Имена интерфейсов/адреса/сырой ответ не печатались и не добавлены в репозиторий. Это подтверждённая ошибка программы, а не доказательство устройства сети VPS. Исторический сырой ответ VPS не сохранён; конкретное содержимое его JSON и наличие назначенного публичного IP установит повторный check после merge.

## Минимальное исправление

Игнорируется только **ровно пустой объект** внутри `addr_info`, соответствующий известному поведению фильтра iproute2. Любой непустой объект без `local`, null/неверный тип, неверный IP, некорректный family/scope/prefixlen или JSON отклоняется. Нельзя пропустить неполную непустую запись даже при наличии корректного публичного адреса в соседней записи.

`scope global` Linux включает и частные адреса; это не синоним публичного адреса. Для принятия по-прежнему нужны все ожидаемые публичные unicast IP в разобранном наборе. Частные, link-local, multicast и IPv4-mapped значения не заменяют ожидаемый публичный IP. Адреса сравниваются в канонической форме, включая IPv6. Неиспользуемый IPv6 не добавляется в ожидания.

## Безопасный результат

Отдельное событие `interface-result` передаёт только два enum: `result` и `reason`. Runner проверяет значения/сочетания, точный набор полей, фазу, режим check и предел одно событие на SSH session. Оно не заменяет ACK, proof или успешный результат admission.

| Результат | Значение |
|---|---|
| DIRECT_PUBLIC_IP_PRESENT | Все ожидаемые адреса найдены в проверенном scope-global наборе; `NONE` или `FILTERED_EMPTY_ENTRIES_IGNORED` |
| PUBLIC_IP_NOT_ON_INTERFACE | Данные корректны, но хотя бы один ожидаемый адрес не найден; `EXPECTED_ADDRESS_ABSENT`. Это отказ, а не заключение о NAT |
| INTERFACE_DATA_INVALID | Неверный JSON/форма/тип/адрес; детали JSON_INVALID, ROOT_NOT_ARRAY, INTERFACE_NOT_OBJECT, ADDR_INFO_NOT_ARRAY, ADDRESS_NOT_OBJECT, LOCAL_MISSING, LOCAL_TYPE_OR_FORMAT_INVALID, ADDRESS_INVALID, FAMILY_MISMATCH, SCOPE_MISMATCH, PREFIX_INVALID и другие ограниченные коды |
| INTERFACE_READ_FAILED | Инструмент отсутствует, timeout, ненулевой статус или лимит вывода; JSON не интерпретируется |

Результат и detail видны в GitHub Summary и безопасной строке console. Нет адресов, имён интерфейсов, DNS hostname, конфигураций, stderr/traceback, ключей, паролей или клиентских данных. `PUBLIC_IP_NOT_ON_INTERFACE` означает отсутствие **в выбранном scope-global представлении**, а не доказанное отсутствие в другом scope/namespace/VRF. Одно `DIRECT_PUBLIC_IP_PRESENT` также не доказывает ownership listener, firewall path, внешнюю доступность или TLS. Все эти проверки сохранены.

Если проверка завершилась на других данных, новый `INTERFACE_DATA_INVALID` с detail отделит это от воспроизведённого случая пустых объектов. Если публичный адрес действительно отсутствует, `PUBLIC_IP_NOT_ON_INTERFACE` продолжит блокировать apply. Никакого автоматического NAT adoption нет.

## Проверки

- Пустые фильтрованные объекты вместе с корректным публичным адресом; только пустые/частные адреса; непустая запись без local; JSON/null/типы/невалидные адреса и IPv6; две ожидаемые семьи и несоответствие.
- Отдельные read failures; безопасный Summary и строгий протокол, неизвестные значения/лишние поля/повторы/wrong phase/apply не принимаются.
- Настоящие bootstrap/framing/PIPE/entry/snapshot на изолированных фикстурах: успех, ошибки JSON/полей, отсутствие ожидаемого IP и ошибка команды. Нет записи state/env/unit или действий с сервисами.
- Чтение реального `ip -j address show scope global` в local/CI без вывода содержимого. Native CI x64/ARM64 теперь сохраняет фактический JSON runner (включая `{}`), добавляя только синтетический ожидаемый адрес в memory-fixture. Не подменяется парсер; настоящий IP не назначается интерфейсу.
- Обязательные native TLS/browser/SQLite/recovery/update/restore, Backend CI, ownership/firewall/CAA/DNSSEC/Origin tests сохранены. Результаты итогового SHA — в PR.

## Если после merge публичного IP нет: только план анализа

Сеть текущего VPS **не подтверждена как NAT**. До выбора реализации нужны обезличенные факты: владелец/провайдер подтверждает соответствие внешнего IP конкретной VM; есть ли one-to-one NAT, floating/routed IP, edge proxy или другая namespace/VRF; куда направлены TCP80/443; кто владеет этими правилами; свободны ли порты; какие host/provider firewall layers участвуют. Проверить другие scope/namespace нужно отдельно read-only, не выводя адреса в публичный отчёт. Сам DNS A, внешний исходящий IP или работающий HTTP:3000 не доказывают эту схему.

После подтверждения допустимы бесплатные варианты отдельного согласованного этапа:

1. **Выделенный provider DNAT до VM + отдельный Caddy.** Доказанные эксклюзивные TCP80/443 mappings на Studio VM, отсутствие конфликтов с VPN/другими приложениями, проверка host и edge firewall. Получить внешнее одноразовое доказательство принадлежности listener, затем сертификат Let's Encrypt HTTP-01, доверенную цепочку/SAN/fingerprint и внешний HTTPS health/API на всех опубликованных IP. До этих доказательств сохранить текущий HTTP. Loopback cutover и исключение обхода HTTP выполняются только после устойчивого HTTPS, по отдельному одобрению.
2. **Согласованный выделенный edge proxy**, если он уже существует и допускает изолированное управление Studio. Не захватывать чужой listener и не редактировать общий proxy автоматически; нужны доказательства upstream ownership, точный HTTPS Origin, очистка поддельных forwarding-заголовков, TLS и сетевой путь до нужной VM. Это не реализовано текущим workflow.
3. **Другой существующий совместимый VPS с прямым IP**, если NAT/edge path нельзя безопасно подтвердить без влияния на VPN. Покупка нового сервера не требуется этим проектом.

DNS-01 способен решить выдачу сертификата без входящего TCP80, но не создаёт доступность HTTPS:443 и не заменяет CAA/DNSSEC/ownership/firewall/TLS. Подключение DNS API/token/plugin — только отдельное согласование; текущий HTTP-01 не требует нового Secret.

Существующий Manage Studio HTTPS пока **не поддерживает автоматический NAT cutover**. Для него нужен отдельный рассмотренный вариант admission с end-to-end доказательствами; нельзя просто удалить проверку прямого IP или считать пустой/невалидный ответ свободным доступом. В этом PR нет изменений VPS, DNS, firewall, routing, VPN, SQLite или HTTP-сайта, нет apply/deploy/merge.

После приёмки и merge владельцем, затем зелёного CI main: Manage Studio HTTPS → main → прежние server_ip/hostname → mode=check → пустой confirmation. Если IPv6 не используется, additional_ip пустой. Передать для анализа только ссылку на run и новые result/reason; не присылать адреса/сырые конфигурации.
