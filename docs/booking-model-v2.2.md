# Внутренняя модель бронирований SQLite — этап 2.2

Основание: актуальный `main` `a56ff9d2756ed6fa54cf82af3e57c47b08078864` с объединёнными PR №6 и №7. Ветка `feat/booking-model-v2.2`. Интерфейс, изображения, правила выбора времени, GitHub Pages workflow и публичный адрес DEMO не меняются.

## Схема

| Таблица | Поля и назначение |
|---|---|
| `resources` | `id`, `name`. Единственная начальная строка: `studio-19-25`, `studio 19.25`. |
| `bookings` | `id`, `resource_id`, `starts_at`, `ends_at`, `status`, `first_name`, `last_name`, `phone`, `created_at`, `updated_at`. |
| `booking_events` | Числовой `id`, `booking_id`, `event_type` (`created`/`cancelled`), `occurred_at`. Контакты в события не копируются. |

Все времена — целые UTC epoch milliseconds; вход модели — московская ISO-дата и минуты от полуночи. Состояния брони — `confirmed`/`cancelled`. Внешние ключи включены; ресурс и бронь с зависимостями не удаляются. Отменённая бронь остаётся в истории. Отдельных таблиц клиентов, оплат, услуг, сессий или запросов нет.

Применённая `0001_foundation.sql` неизменна. Версия `0002_booking_model.sql` атомарно перестраивает `bookings`, сохраняя ID, интервалы и статусы, и назначает старым строкам единственный ресурс. Контактов и служебных дат в прежней схеме не было: для таких строк сохраняется NULL. Поддельных контактов/исторических событий не создаём. Для **новых** строк все контакты и даты обязательны через SQL-trigger, заполненные поля нельзя обнулить UPDATE. Историю существующих данных модель не подменяет. Отмена старой confirmed-брони создаёт только фактическое событие отмены и `updated_at`.

Миграции применяются существующим runner: последовательные версии, SHA-256 всего применённого префикса, BEGIN IMMEDIATE, атомарный SQL + журнал, повтор без изменений, ненулевой exit при ошибке. Ошибка перестройки откатывает и DDL, и данные; автоматического down нет. Перед обновлением рабочей базы нужен online snapshot и проверка восстановления по [инструкции](backend-local-setup.md).

## Контракт модели для будущего API

Модуль `src/server/bookings.ts` помечен `server-only`, принимает открытое серверное SQLite-соединение. React его не импортирует. Транспорт/авторизация/REST API пока отсутствуют.

- `createBooking(db, {id, resourceId, date, start, end, firstName, lastName, phone}, now?)` возвращает сохранённую `confirmed`-бронь после COMMIT. `now` по умолчанию — серверные часы; явное значение нужно детерминированным тестам, не должно поступать от HTTP-клиента.
- `cancelBooking(db, id, now?)` атомарно меняет статус и дату, сохраняет событие. Повтор отмены ничего не меняет. Это внутренняя операция: будущий транспорт обязан проверять полномочия; клиентская самостоятельная отмена не разрешена.
- Контакты проверяются общей `validateContact`, телефон нормализуется в `+79XXXXXXXXX`; имена обрезаются по краям. `validateInterval` — тот же источник правил даты/времени, что у UI. Появившаяся `.ts` в импорте `availability → studio` нужна прямому Node 24 CLI, не меняет расчёты.
- ID и resourceId — непустые строки до 128 символов без управляющих символов и внешних пробелов. Генерацию стабильного ID должен обеспечить будущий транспорт/клиент; ID не является разрешением доступа.
- Caller обязан **повторять тот же ID** после неизвестного результата/обрыва. Тот же ID и канонические контакты/ресурс/интервал возвращают прежнюю запись без второго события, в том числе после истечения даты или отмены. Другой payload с тем же ID даёт `BOOKING_ID_CONFLICT`. Новая самостоятельная бронь требует нового ID. Одинаковый телефон не ограничивает число независимых броней.
- Вложенная внешняя транзакция отклоняется: модель должна возвращать успех только после собственного COMMIT. Никаких HTTP-вызовов/await внутри writer-транзакции нет.

Ошибки имеют безопасные коды: `INVALID_INPUT`, `INVALID_CONTACT`, `INVALID_INTERVAL`, `RESOURCE_NOT_FOUND`, `BOOKING_NOT_FOUND`, `BOOKING_ID_CONFLICT`, `BOOKING_OVERLAP`, `DATABASE_BUSY`, `STORAGE_FAILURE`, `TRANSACTION_ACTIVE`. SQL, пути и контакты в ошибку не включаются. Будущий API должен сопоставить коды HTTP-статусам, ограничить размер запроса и обеспечить защиту от злоупотребления. При `DATABASE_BUSY`/неизвестном результате повторяют тот же ID; постоянную ошибку диска нельзя бесконечно скрывать повторами.

## Правила и конкурентность

Московская зона `Europe/Moscow`, каждый день 09:00–23:00, 28 слотов, шаг 30 минут, минимум 60 минут, максимум один рабочий день (14 часов), без буфера. Последний час — 22:00–23:00. Прошлые даты/начала запрещены, точный текущий старт допустим. Окно включает сегодняшнюю московскую дату и дату +3 календарных месяца; короткий месяц ограничивается последним днём. Период и текущее время проверяются при **новом** создании под writer-lock; повтор уже созданного запроса не становится новым бронированием.

`BEGIN IMMEDIATE` сериализует независимых писателей, SQL-trigger проверяет пересечение `[start,end)` только confirmed-броней того же ресурса. Пересечение запрещено и при UPDATE ресурса/времени/статуса. Соседние разрешены; отменённые не мешают; разные ресурсы совместимы. Один предварительный SELECT вне транзакции не используется. Изменение брони и событие фиксируются либо вместе, либо никак. Событие создания одно на ID; повтор создания/отмены не дублирует историю.

Сохранены WAL, `synchronous=FULL`, `foreign_keys=ON`, `trusted_schema=OFF`, bounded busy timeout, приватные файлы вне сборки, health write/check и online backup. Один файл на локальном диске одного VPS: нет распределённой блокировки или нескольких серверных компонентов. Защита от потери питания зависит также от выполнения fsync самим диском/файловой системой; FULL не заменяет независимую копию.

## Проверки и границы этапа

`npm run test:integration` использует настоящую SQLite и отдельные Node-процессы. Проверяются создание/контакты/события, пересечения и соседство, разные ресурсы, повтор ID и конфликт payload, отмена/освобождение, параллельные писатели/повторы, busy timeout, ошибочный event insert с rollback, реальный SQLITE_FULL, SIGKILL до/после COMMIT, reopen, backup/restore, перенос старых строк и rollback неудачной миграции. Общие unit/E2E и SERVER/DEMO проверки сохраняются. Итоги запуска и ссылка Backend CI приводятся в PR.

Локальная проверка 18 октября 2026: **115 unit, 55 integration (37 модели + 18 инфраструктуры), 26 E2E** прошли. TypeScript, lint, SERVER build, Node DEMO build и статический DEMO build прошли. Реальная SQLite **3.53.4**, better-sqlite3 **13.0.3**, Node **24.19.0**. HTTP: три цикла 200→503→200 и readonly→503→200; отрицательный контроль постоянного отказа ожидаемо получил exit 1 и успешно завершил cleanup. DEMO собрана с недоступным SQLite path/невалидной DB-конфигурацией; аудит 29 файлов не обнаружил credential patterns, private/server-файлов или отсутствующих ресурсов. E2E выполнены на статическом `/loft-booking/` для телефона и компьютера. Изменений Pages workflow и применённой миграции 0001 нет. Backend CI должен подтвердить итоговый коммит отдельно; ссылка/статус — в PR, локальные проверки не подменяют CI.

Этап готовит хранение для 2.3, но не открывает API создания/чтения/отмены, не подключает интерфейс к базе и не собирает реальные персональные данные. В SERVER запись в UI по-прежнему отключена; DEMO использует вымышленные данные, не импортирует SQLite и собирается без БД. Админ-панель, уведомления, оплата, VPS и merge не выполняются.

Перед 2.3 нужно согласовать транспортный контракт, выдачу/повтор ID, правила доступа (в том числе отмены), защиту API и правовые основания обработки контактов. Для старых строк потребитель обязан корректно обрабатывать nullable контакты/даты. Статические SQL-проверки часов используют текущий UTC+3; изменение московской зоны потребует новой миграции. Не следует обходить модель произвольным SQL: динамическое окно, валидация имён и идемпотентность находятся в модели, а доступ к файлу SQLite даёт полные права на данные.
