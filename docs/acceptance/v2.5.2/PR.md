# feat: Studio installer, encrypted backups and explicit restore (2.5.2)

Продолжение существующего draft PR №12. Владелец запускает Install через Actions из main с одним `server_ip`; проверенный immutable SHA собирается off-VPS для Ubuntu 24.04 x64/ARM64. Исправный same-SHA запуск не заменяет релиз и не перезапускает процесс. SQLite/photos/settings находятся отдельно от кода.

По новому согласованному требованию install, daily backup, pre-update backup и restore используют одинаковую SSH-политику с отключённой проверкой host key. Она задаётся только параметрами SSH-процесса Studio; глобальная конфигурация runner/VPS и обычный SSH владельца не меняются. **MITM/ошибочный IP могут перехватить root-пароль и подменить данные до шифрования.** Пароль передаётся только из GitHub Secret через отдельное окружение sshpass, не argv/файлы/логи. Дополнительный Secret ключей хоста удалён.

Перед update обязателен согласованный SQLite Backup API snapshot + photos/settings, GPG AES-256, private Release upload и обратная проверка hash. Без verified receipt миграции не начинаются. Daily 03:15 Москва делает максимум две попытки, сохраняет 7 успешных дней; completed pre-update ограничены тремя, незавершённые закреплены. Подтверждённый дефект cleanup исправлен: tag удаляется до Release, чтобы отказ API не оставлял невидимый orphan tag; частичное удаление завершается повтором. Только HTTP404 допускается как уже удалённый объект, не 403/5xx/transport errors.

Обрывы до/во время/после снимка, передачи и COMMIT не дают ложного SUCCESS. Abort разрешён только при соответствующих nonce/схеме; неизвестное состояние и несовместимая committed migration сохраняют DB/защищённую копию, без автоматического возврата старого кода. Потерянный ответ о committed ready-версии разрешается проверкой при повторном запуске. Restore требует list/tag/явное `RESTORE STUDIO 19.25`, decrypt/hash/schema/version checks; текущий DATA/WAL сохраняется рядом. Поддерживается исходная и чистая независимая установка; внешние операции в тестах mocked.

Нужны Secrets `STUDIO_SSH_PASSWORD`, `STUDIO_BACKUP_TOKEN`, `STUDIO_BACKUP_PASSPHRASE` (>=32); Variables `STUDIO_BACKUP_REPOSITORY`, `STUDIO_BACKUP_SERVER_IP`. Backup repo отдельный, private, initialized; fine-grained token только к нему с ContentsRW + MetadataRead. Обычный GITHUB_TOKEN не используется для cross-repo. Не включать immutable Releases/правила служебных тегов, запрещающие ротацию.

Root создаёт только managed user/dirs/releases/unit, запускает свои sandbox CLI и управляет только Studio. VPN/proxy/firewall/DNS/sshd не меняются. Временный `http://IP:PORT` — только вымышленные контакты; внутренние проверки и внешняя reachability разделены. HTTPS не настраивается.

Проверки: 51 installer/security/fault tests с настоящими SQLite/GPG/filesystem и имитацией внешних операций; native Installer CI x64/ARM64 проверяет install/no-op (включая PID)/update/restore/clean-host restore/failures/rollback/canary/network. Backend CI повторяет unit/integration/HTTP/E2E/typecheck/lint/SERVER/Node DEMO/static DEMO. Итоговые результаты относятся к последнему SHA ветки: [Checks](https://github.com/jurist77/loft-booking/pull/12/checks). Старые зелёные runs не подменяют новый прогон.

На настоящих VPS/SSH и рабочем backup repo ничего не запускалось. Не проверены реальные VPN peaks/reboot/ресурсы/публичный маршрут/права и квоты Releases. Непрерывная потеря связи может потребовать ручного разбора; schedule/email GitHub не дают SLA. Шифрование не компенсирует отсутствие SSH host authentication. UI/DEMO/API бронирования не изменены, merge не выполняется.
