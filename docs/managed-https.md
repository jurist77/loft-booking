# Управляемый HTTPS Studio 19.25

Этот PR готовит ручную установку HTTPS. Реальный VPS не проверен и не изменён: аудит 42491756270 остаётся исходной точкой, а не доказательством готовности TLS. Не запускайте apply до приёмки PR, merge владельцем и успешных проверок текущего main.

## Схема и границы поддержки

Интернет → Caddy TCP 80/443 → Studio `127.0.0.1:<managed port>` → существующая SQLite. DEMO, интерфейс, миграции, VPN, SSH, reverse proxy других приложений и правила firewall не меняются. Caddy использует бесплатный Let's Encrypt HTTP-01, автоматически продлевает сертификат; токен DNS-провайдера (DuckDNS/dynv6) не нужен. Зарегистрировать hostname и поддерживать A/AAAA должен владелец. Это не DNS-01 и не IP-сертификат.

Первый выпуск намеренно принимает только Ubuntu 24.04/systemd x64/ARM64 с установленной управляемой Studio, свободными TCP 80/443, непосредственно назначенным публичным IP, неактивным UFW и доказанно пустыми nftables/iptables/legacy rulesets с ACCEPT policies. Наличие фильтрации, неизвестный инструмент, NAT, чужой listener, неуправляемые одноимённые файлы/пользователь/units, неоднозначная принадлежность сокетов, другой FragmentPath/неизвестные systemd drop-ins или несовпадение конфигурации блокируют изменения. Скрипт **не открывает порты и не изменяет firewall**, не адаптирует чужую инфраструктуру. Для другой конфигурации нужен отдельный анализ.

Проверяются оба семейства IP. Публикуйте AAAA только если IPv6 действительно настроен и достижим с runner. Вводится один адрес каждого опубликованного семейства; несколько A/AAAA и CNAME пока не поддерживаются. IPv6-only сервер тоже требует совместимого SSH/runner egress. Ограниченная доступность IPv6 на GitHub runner приводит к отказу, а не к пропуску проверки. Адрес должен быть публичным. Hostname — канонический ASCII FQDN любого DNS-провайдера: минимум два label, каждый 1–63 символа, максимум 253 символа суммарно, lowercase, без завершающей точки. IDN передавать как корректные A-label (`xn--…`). Схема, путь, порт, IP вместо имени, wildcard, underscore, пробелы и специальные локальные зоны отклоняются. Поддержка FQDN не означает разрешение доступа: оба независимых резолвера должны подтвердить точное соответствие всех A/AAAA и применимый CAA.

Caddy 2.11.9 загружается из официального GitHub Release по закреплённым SHA-256 отдельно для x64/ARM64. Проверяются архив и ELF. Нет установки стороннего apt-repository, Docker, отдельной БД или сборки Next.js на VPS. Обновление версии Caddy или смена hostname требуют отдельного рассмотрения; повторный apply не выполняет скрытое обновление бинарника.

## Перед первым запуском — действия владельца

1. Принять PR и объединить его вручную. Дождаться зелёных `Check backend foundation`, `Check universal installer` (обе архитектуры, включая TLS/browser) и `Check Studio HTTPS` на **текущем main**.
2. Убедиться, что текущая Studio установлена универсальным установщиком, здорова и имеет резервную копию. При необходимости сначала обновить Studio проверенным установщиком. HTTPS-контроллер не выполняет миграций и не изменяет SQLite.
3. У выбранного DNS-провайдера установить A на нужный IPv4. Удалить ошибочный AAAA либо обеспечить корректный IPv6 и указать его как additional_ip. Проверить отсутствие конфликтующего CAA. Токен DNS-провайдера не передавать workflow.
4. Сохранить существующий `STUDIO_SSH_PASSWORD` в GitHub → Settings → Secrets and variables → Actions → Secrets. Подключение root:22. Проверка SSH host key отключена **только в операциях Studio** по согласованной политике. **MITM может подменить сервер и перехватить root-пароль**; проверка DNS/TLS не устраняет этот риск SSH. Глобальные настройки SSH не меняются.
5. Сохранить независимый доступ владельца по SSH для ручной диагностики. Не закрывать рабочий HTTP вручную заранее. Использовать только вымышленные контакты до приёмки и правовой готовности.

## Run workflow: check

GitHub → Actions → **Manage Studio HTTPS** → Run workflow → branch **main**:

- `server_ip`: публичный IPv4 или IPv6 сервера;
- `hostname`: зарегистрированный публичный FQDN, например `studio1925.dynv6.net`, без схемы, пути и порта;
- `additional_ip`: адрес другого семейства, если опубликован в DNS;
- `mode`: `check`;
- `confirmation`: пусто.

Check выполняет только чтение: два публичных DNS-over-HTTPS resolver (A/AAAA/CAA), доступность production ACME directory и корректность часов, владельцев сокетов/процессов Studio, RAM/диск, адреса интерфейсов, UFW и оба backend firewall, управляемые файлы/units. Отчёт содержит только безопасные коды; конфигурации, IP, hostname, пароли и клиентские данные не печатаются. Пароль передаётся sshpass через окружение, не аргументы/файлы/артефакты.

`CHECK_CANDIDATE_ACTIVE_PROOF_REQUIRED` означает **кандидат, а не READY**: на свободном порту нет HTTP-сервиса, поэтому read-only запрос не доказывает входящий ACME-путь. Неизвестный внешний путь нельзя объявить проверенным. `CHECK_EXISTING_HTTPS` включает проверку сертификата, health, GET availability и закрытого backend. `CHECK_MANAGED_TLS_STOPPED` требует анализа и отдельного apply для запуска только собственного Caddy. Ошибка/неопределённость — отказ, без изменений.

## Run workflow: apply — только после отдельного разрешения

Те же параметры, `mode=apply`, точное `confirmation=ENABLE STUDIO HTTPS`. По умолчанию ничего не применяется, автоматического deploy по push/расписанию нет.

Порядок:

1. Повторная проверка под общим installer lock; при неизвестном состоянии отказ.
2. В рамках явно разрешённого apply на свободных 80/443 кратковременно запускаются ограниченные диагностические HTTP-listeners в памяти. Runner проверяет одноразовый ответ по каждому A/AAAA. При неуспехе они закрываются, конфигурация и работающий HTTP Studio не меняются. Это проверяет провайдерский путь, но не гарантирует доступность всех узлов Let's Encrypt; получение настоящего сертификата обязательно отдельно.
3. Создаются только собственные пользователь `studio1925tls`, `/opt/studio1925-https`, `/etc/studio1925-https`, `/var/lib/studio1925-tls` и `studio1925-tls*` units. Данные и ключи Caddy закрыты; приложение не получает доступа к ключам. Unix admin socket закрыт от публичного доступа. HTTP/3 отключён: UDP443 не используется.
4. Caddy получает production сертификат Let's Encrypt. Старый публичный HTTP Studio остаётся работающим. Проверяются цепочка доверия, SAN, срок (>7 суток), локальный и внешний HTTPS health и GET availability; fingerprint должен совпасть на всех опубликованных адресах.
5. Только после этих доказательств атомарно меняются управляемые env/unit Studio: точный `API_PUBLIC_ORIGIN=https://<hostname>`, `API_TRUST_PROXY=true`, `API_ALLOW_INSECURE_TEST_HTTP=false`, bind **127.0.0.1**. Перезапускается только Studio. Caddy удаляет поддельные forwarding/client-IP заголовки и устанавливает собственные. Внешний POST Origin проверяется существующим API; разрешающий CORS не добавляется.
6. Повторно проверяются владельцы/адреса сокетов, настоящий HTTPS/API и недоступность backend на опубликованных IP. Kernel-проверка требует IPv4 loopback, без публичных IPv4/IPv6 listeners Studio. Внешняя отрицательная проверка охватывает только введённые/опубликованные адреса, не неизвестные адреса сервера.
7. Записывается durable `public-verified`, затем committed HTTPS. Автозапуск Caddy и свои timers включаются только для управляемых units. Результат SUCCESS требует внешней проверки; никакого POST в рабочую базу нет.

Скрипт не обещает нулевого влияния на весь VPS: CPU, диск и systemd manager общие. `daemon-reload` перечитывает unit definitions, но не перезапускает чужие службы. Ресурсные/сетевые изменения параллельно с apply запрещены организационно; обнаруженные изменения фильтрации блокируют переход. Полностью исключить гонку с независимым root-администратором невозможно.

## Частичный сбой, повтор и возврат

До cutover прежний HTTP работает. Во время собственного restart возможен короткий перерыв. Корневой checkpoint и recovery timer (каждые 30 секунд и после boot) защищают от разрыва SSH, SIGKILL и перезагрузки; общий lock исключает одновременный install/update/restore. Незавершённый checkpoint блокирует эти операции.

До `public-verified` восстановление возвращает **предыдущие env/unit/release**, останавливает только собственный Caddy. Это возврат к прежнему техническому HTTP, поэтому реальные контакты до завершения не использовать. **SQLite никогда не откатывается**: новые брони сохраняются. После `public-verified` recovery завершает HTTPS и не возвращает публичный HTTP. Неизвестные ручные изменения файлов или другой релиз не затираются: checkpoint остаётся, результат MANUAL_REVIEW_REQUIRED.

Потеря SSH/ответа после COMMIT не доказывает неуспех. Подождать recovery, запустить check и оценить отчёт. Не менять managed env вручную и не запускать принудительный HTTP downgrade. Повторный apply после успешного HTTPS проверяет его и не перезапускает Studio; может восстановить остановленный собственный Caddy при свободных портах. Неоднозначное состояние требует ручного анализа. Ошибка подготовки до записи owner metadata может оставить собственные staged files/user: старый HTTP сохраняется, но повтор блокируется до проверенной ручной уборки; автоматического удаления неизвестных файлов нет.

Полный возврат с уже принятого HTTPS или удаление Caddy не автоматизированы: это отдельная согласованная операция с проверкой данных и сетевого пути. Откат приложения не равен откату схемы БД.

## Install / update / restore после HTTPS

HTTPS metadata — часть управляемого состояния приложения и encrypted backup manifest (только hostname, без TLS private keys). Текущие lifecycle controls применяются независимо от выбранной версии app-артефакта. Install/update сохраняют HTTPS Origin, proxy trust, loopback и выбранный внутренний порт. Если он занят — отказ вместо незаметной смены upstream.

Restore на существующий HTTPS target сохраняет **его собственный hostname**, включая восстановление старого HTTP backup. Restore HTTPS backup на HTTP/uninstalled target блокируется **до изменений**: сначала установить Studio на target, согласовать DNS, включить и проверить HTTPS, затем выполнить restore. Автоматически переносить старый hostname, секретные ключи сертификата или выставлять контакты в HTTP нельзя. Restore прежней app-версии использует текущие проверенные lifecycle controls; применимость старого app к схеме БД по-прежнему проверяет существующий установщик. Не обходить эти ограничения старым workflow revision.

## Renew и мониторинг

Caddy автоматически продлевает сертификат, пока DNS и входящий TCP80 доступны Let's Encrypt, а процесс/диск/часы исправны. Не выполнять принудительные repeated issuance: действуют rate limits CA. Конфигурация использует Let's Encrypt, не подменяет её self-signed сертификатом при ошибке.

- Локальный `studio1925-tls-monitor.timer` ежечасно проверяет доверенный TLS, hostname, срок >7 суток, health/API. Ошибка даёт ненулевой status и безопасный `STUDIO_TLS_ATTENTION_*` в журнале **своей** службы. Сам по себе journal не доставляет сообщение владельцу.
- В GitHub → Settings → Secrets and variables → Actions → **Variables** установить `STUDIO_HTTPS_MONITOR_HOSTNAME=<hostname>`, затем `STUDIO_HTTPS_MONITOR_ENABLED=true`. По умолчанию монитор выключен и этот PR его не включает. Workflow **Monitor Studio HTTPS** ежечасно проверяет публичный TLS/DNS/health без SSH/POST/секретов.
- В персональных GitHub Settings → Notifications включить уведомления Actions о failed workflows и проверить доставку на нужное устройство/email. Затем ручной Run workflow → `test_notification=true`: он намеренно падает **без сети**. Убедиться, что сигнал получен; затем обычный запуск должен пройти. Внешний платный сервис не нужен.
- GitHub schedules могут задерживаться или отключаться после длительной неактивности; это не SLA. Владелец обязан контролировать, что монитор действительно запускается. Ошибка требует проверки DNS, срока, диска, Caddy и ACME до истечения сертификата. Workflow не чинит сеть и не перезапускает VPS.

Нельзя считать HTTPS продление эксплуатационно проверенным до получения настоящего сертификата на выбранном VPS и приёмки мониторинга. В CI проверяется настоящее TLS/автопродление с короткоживущим **изолированным внутренним CA**, без запросов к production ACME.

## Приёмка и ограничения

Обязательный Installer CI x64/ARM64: реальный systemd/Caddy/Next, отдельная временная SQLite, доверие тестовому CA без ignoreHTTPSErrors, полный браузерный путь и COMMIT, потерянный ответ/тот же UUID, Origin/IP spoof защита, реальный recovery timer после hard crash, повтор/update/restore без HTTP downgrade, неизменность соседней UDP443 canary службы/файлов/firewall. Это тесты на disposable GitHub runner, **не на VPS**. Unit fixtures проверяют DNS/CAA/firewall/ownership/SSH отказ и неизвестные состояния. Никакие фикстуры не включаются production inputs.

На реальном VPS workflow делает только GET health/availability и проверки TLS/порта, **не создаёт броней**. После отдельного разрешения проверить пять экранов без отправки реальных данных. Если требуется ручной тест COMMIT, создать отдельную изолированную SQLite/инстанс по отдельному плану, не направлять тест в рабочую БД. Текущая обязательная браузерная проверка записи выполняется только в CI.

Первый PR не подтверждает фактический внешний DNS/порты, выдачу Let's Encrypt и безопасность конкретного VPS: это устанавливается check и отдельно разрешённым apply. Не вводите реальные контакты до приёмки HTTPS, backup/restore и юридических оснований обработки.

Подробные коды и повторная DNS-only проверка: [DNS diagnostics](https-dns-diagnostics.md). SERVFAIL не означает отсутствие AAAA/CAA и не разрешает apply.
