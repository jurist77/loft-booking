# Локальный SERVER с SQLite

Нужны Git, **Node.js 24 LTS** и npm. Docker/PostgreSQL не нужны. Поддерживаемая среда — Linux (Ubuntu 24.04 на будущем VPS) или macOS; на Windows используйте WSL2. Драйвер `better-sqlite3` содержит native-модуль: устанавливайте `npm ci` на той ОС/архитектуре/Node major, где приложение будет запускаться. Если готовый бинарник недоступен, понадобятся Python 3, make и C++ compiler; проверки TLS отключать нельзя.

В существующем репозитории:

```bash
npm ci
npm run db:env
npm run db:init
npm run db:migrate
npm run db:migrate
npm run db:check
npm run dev:server
```

`db:env` создаёт только новый `.env.sqlite.local` (0600). По умолчанию база находится **в соседнем с checkout каталоге** `.studio1925-local/studio.sqlite`; данные переживут пересборку и смену релиза. Существующий env-файл не перезаписывается. Старые `.env.local`/`.env.test.local` с PostgreSQL не используются для подключения; они не удаляются автоматически. Проверьте их вручную и удалите ненужные секреты после принятия перехода. Паролей у SQLite нет; защиту обеспечивает ОС.

`db:init` создаёт каталог 0700 и файл 0600; повторный запуск сохраняет данные. `db:migrate` применяет версию один раз, повтор возвращает **0**. Запуск SERVER без init/миграций даёт безопасный 503, а не пустую новую базу.

Для существующей базы перед обновлением сделайте `db:backup` в новый файл по инструкции ниже. Этап 2.2 применяет только новую `0002_booking_model.sql`: старые интервалы сохраняются и привязываются к студии, неизвестные контакты/даты остаются пустыми. `0001_foundation.sql` и её checksum не меняются. Не удаляйте базу и не редактируйте журнал миграций. После обновления запустите `db:migrate` и `db:check`; повторный migrate не добавляет записей. Подробности: [модель бронирований](booking-model-v2.2.md). Тесты используют только вымышленные контакты; интерфейс пока не записывает ничего в SQLite.

В другом терминале:

```bash
curl -i http://127.0.0.1:3000/api/health
```

Ожидается 200 и `{"status":"ok"}`. Проверяются целостность и маленькая **зафиксированная запись**, поэтому readonly/full/I/O не выдаются за готовность. При недоступности — 503 и `{"status":"unavailable"}`, без путей и SQL. Оптимизированный запуск: остановить dev через Ctrl+C, затем `npm run build:server` и `npm run start:server`. Приложение слушает только 127.0.0.1. SERVER-интерфейс с этапа 2.4 проходит пять экранов и сохраняет бронь через API. DEMO остаётся отдельным режимом.

Интерфейс этапа 2.4 использует API этапа 2.3: `GET /api/availability?date=YYYY-MM-DD`, `POST /api/bookings`. Использовать только вымышленные контакты в тестовой БД. POST требует `Origin: http://127.0.0.1:3000`, JSON до 4096 байт и UUID. Настройки `API_PUBLIC_ORIGIN`/`API_TRUST_PROXY` описаны в `.env.example`; при другом порте изменить Origin. [Контракт, curl-примеры и ограничения защиты](booking-api-v2.3.md). Не включать доверие proxy на публично доступном порту Next.

## Онлайн-копия

Укажите **новый абсолютный путь вне checkout**. Существующая копия не перезаписывается:

```bash
npm run db:backup -- --to /absolute/private-backups/studio-2026-10-18.sqlite
```

Создаётся согласованный snapshot через SQLite backup API с учётом WAL. Приложение можно оставить запущенным. Команда проверяет integrity/foreign keys, права 0600, fsync и атомарно публикует готовый файл; ошибка даёт ненулевой exit code. **Не копируйте только живой `studio.sqlite` через cp:** последние записи могут находиться в `-wal`. Локальный snapshot ещё не является зашифрованной внешней копией — схема restic описана в [эксплуатации](sqlite-operations.md).

## Проверка восстановления

Для учебного восстановления выбирайте **другой отсутствующий файл**, не рабочую базу:

```bash
SQLITE_PATH=/absolute/restore-test/studio.sqlite npm run db:restore -- --from /absolute/private-backups/studio-2026-10-18.sqlite
SQLITE_PATH=/absolute/restore-test/studio.sqlite npm run db:check
SQLITE_PATH=/absolute/restore-test/studio.sqlite npm run db:migrate
```

`db:restore` проверяет копию и создаёт новую базу; существующий файл не заменяет. Команда использует SQLite backup API и не меняет источник. Для production-восстановления сначала остановить приложение, сохранить весь старый каталог с WAL/SHM и только затем восстанавливать — [пошаговый runbook](sqlite-operations.md#восстановление-и-проверка).

## Тесты

```bash
npm test
npm run test:integration
npm run typecheck
npm run lint
npm run build:server
npm run test:api:http
npm run test:server:http
npm run test:server:http:failure
npm run build
npm run test:demo:isolation
npm run preview:demo
```

Интеграционные и HTTP-тесты сами создают и удаляют **свои временные** SQLite-каталоги. Локальная рабочая БД не используется. HTTP-тесту нужен свободный порт **3011**. Проверяются три цикла 200 → недоступность файла → 503 → восстановление → 200 в одном Next.js, а также отказ записи. Отрицательный контроль запускает отдельную команду, оставляет её базу недоступной и принимает только ожидаемый exit 1 по timeout с 503, восстановлением БД и завершением Next.js. Исправления HTTP keep-alive из PR №6 сохранены.

API HTTP-тест использует свободный **3012** и собранный SERVER; проверяет настоящие конкурентные POST, повторы, доступность, ошибки, отказы, восстановление и limiter. `test:demo:isolation` теперь собирает Node DEMO, проверяет страницу 200 и все API 404 на **3013**, завершает Next, затем собирает/аудирует static DEMO. Обе сборки проверяются с недоступной БД и невалидными серверными настройками. Не запускать эти проверки одновременно с другой сборкой того же target.

Playwright: `npm run test:e2e` для Node DEMO либо `PLAYWRIGHT_BASE_URL=http://127.0.0.1:4173/loft-booking/ npm run test:e2e` для готового preview. Нужен Chromium согласно README. Сначала остановите SERVER, если он занимает порт 3000. Не запускайте разные сборки одного target одновременно.

## Диагностика

| Симптом | Действие |
|---|---|
| 503 / `DATABASE_OPERATION_FAILED` | Проверить APP_MODE=server, абсолютный SQLITE_PATH, `db:check`, наличие свободного места и inode (`df -h`, `df -i`). Не вставлять БД/контакты/логи с путями в публичный отчёт. |
| Нет файла | Выполнить init и migrate только для действительно нового окружения; при потере рабочей БД восстанавливать копию, не создавать пустую замену. |
| Права доступа | Каталог принадлежит пользователю приложения и имеет 0700, DB/WAL/SHM — 0600; symlink/hardlink запрещены. Не применять chmod 777. |
| SQLite busy/locked | Другой процесс держит запись. Транзакции должны быть короткими. Подождать завершения миграции; не удалять lock/WAL/SHM. Busy timeout ограничен 50–5000 мс, по умолчанию 1000. |
| `HISTORY_MISMATCH` | Вернуть исходные применённые SQL из Git. Не править хэши/журнал вручную. |
| Повреждение/диск readonly/full | Остановить запись, устранить проблему хранилища; затем check или восстановление проверенного snapshot. Скрипт не стирает БД автоматически. |
| `/api/health` 404 | Запущен DEMO; endpoint есть только в SERVER. |
| Ошибка native-модуля | Node 24, нужная ОС/архитектура; повторить npm ci на целевой машине. Не переносить node_modules с Mac на Linux. |

Штатная остановка — Ctrl+C или будущий `systemctl stop`; отдельной команды остановки БД нет. Ничего не удаляет базу при обычной остановке.

## Проверка через интерфейс

После запуска SERVER открыть на своём компьютере http://127.0.0.1:3000, выбрать будущую дату/интервал, ввести только вымышленные контакты и дождаться подтверждения с UUID. После обновления страницы интервал занят. Это настоящая запись в вашей тестовой БД, публичной отмены нет. При неизвестном результате повторить в той же вкладке, не перезагружать: попытка хранится только в памяти. [Подробный путь и состояния](server-client-v2.4.md).

После `npm run build:server` и `npm run test:demo:isolation` выполнить `npm run test:server:ui`: отдельные временные БД/Next/preview на 3014/4174, 20 SERVER E2E и прежние 26 DEMO E2E. Нужен Chromium. `npm run test:server:ui -- --capture-only` создаёт материалы 2.4 без повторного запуска тестов. [Отчёт и снимки](acceptance/v2.4/README.md). Рабочая БД не используется.
