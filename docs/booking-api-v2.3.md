# API бронирований — этап 2.3

Основание — `main` `c4da080bb267735eec54eb540e5c3c0eed0225dd` после слияния PR №8. Один Next.js Node + better-sqlite3, существующие миграции 0001/0002, без новых таблиц/зависимостей/процессов. Только `APP_MODE=server`. UI к API **не подключён**; пять экранов и GitHub Pages DEMO не меняются.

## GET /api/availability

```http
GET /api/availability?date=2026-10-20&resourceId=studio-19-25
```

`date` обязателен: строго YYYY-MM-DD, существующая календарная дата от сегодняшней **по Москве** до +3 календарных месяцев включительно. Прежний clamp короткого месяца сохранён. `resourceId` необязателен, по умолчанию `studio-19-25`. До 128 символов, без управляющих символов и внешних пробелов. Пустые/повторные/неизвестные параметры запрещены; полный URL до 2048 символов.

```json
{
  "date": "2026-10-20",
  "resourceId": "studio-19-25",
  "timezone": "Europe/Moscow",
  "busy": [{ "start": "12:00", "end": "14:00" }]
}
```

HTTP 200, `busy: []` при свободном дне. Только confirmed-интервалы указанного ресурса, по возрастанию начала; cancelled исключены. Время HH:MM — **местное московское время указанной даты**, не UTC; интервалы полуоткрытые `[start,end)`. Соседние записи могут возвращаться отдельными элементами и не конфликтуют. Прошедшие часы сегодняшнего дня могут присутствовать: запрет их выбора обеспечивают общие правила модели/интерфейса. Имён, телефонов, ID броней, событий или служебных дат в SELECT и ответе нет.

Это текущий снимок, не обещание свободного места до POST. Ответы и ошибки имеют `Cache-Control: no-store, max-age=0`, `X-Content-Type-Options: nosniff`; Route Handler force-dynamic. Прокси также не должен кэшировать `/api/`.

## POST /api/bookings

Обязательны `Origin`, совпадающий с `API_PUBLIC_ORIGIN`, и `Content-Type: application/json` (допустим `; charset=utf-8`). Сжатие тела не принимается. Тело — плоский JSON-объект, **ровно восемь текстовых полей**:

```json
{
  "requestId": "12345678-1234-4123-8123-123456789abc",
  "resourceId": "studio-19-25",
  "date": "2026-10-20",
  "start": "12:00",
  "end": "14:00",
  "firstName": "Тест",
  "lastName": "Пример",
  "phone": "+79000000000"
}
```

Пример использует только вымышленные контакты. Для новой попытки генерировать `crypto.randomUUID()`; сохранять ID в памяти до определённого результата. При неизвестном результате повторять тот же ID и данные.

- `requestId`: каноническая UUID-форма 8-4-4-4-12, RFC variant, версия 1–8; регистр нормализуется в lower case. Рекомендуется случайный UUID v4. ID не является авторизацией.
- `resourceId` обязателен и проверяется как в GET; несколько ресурсов уже поддерживаются моделью.
- `date`: строгая существующая календарная дата. Новая бронь проходит серверное окно/запрет прошлого; повтор уже созданной операции может содержать прошедшую дату.
- `start`/`end`: HH:MM с ведущими нулями, 00:00–23:59. Рабочие часы, 30-минутный шаг, минимум час и отсутствие пересечений проверяет **существующая модель**, а не новая копия правил API. 09:00–23:00, последний час 22:00–23:00, максимум 14 часов.
- `firstName`/`lastName`: до 80 символов каждое до trim; дальше общая `validateContact` (буквы, пробел, дефис и допустимые апострофы, обязательность). `phone`: до 32 символов исходного ввода; тот же российский мобильный валидатор нормализует в `+79XXXXXXXXX`.
- Неизвестные/дублированные ключи (включая Unicode-escape одного имени), массивы, вложенные значения, неверный UTF-8, комментарии и trailing comma отклоняются. Максимум **4096 фактических байт**, не только Content-Length; чтение тела ограничено **5 секундами**. Нарушение плоского текстового JSON-контракта — INVALID_JSON; остальные ошибки схемы — INVALID_INPUT.

Успех после COMMIT, HTTP **201**:

```json
{
  "bookingId": "12345678-1234-4123-8123-123456789abc",
  "status": "confirmed",
  "date": "2026-10-20",
  "start": "12:00",
  "end": "14:00",
  "resourceId": "studio-19-25"
}
```

Контакты не возвращаются. `bookingId = requestId` после нормализации UUID. Модель получает время сервера под BEGIN IMMEDIATE, проверяет ресурс/правила, SQL-trigger проверяет confirmed-пересечения **того же ресурса**, бронь и created-event фиксируются вместе. Параметризованные запросы, никакого SQL из тела. Соседство и параллельные интервалы разных ресурсов разрешены. Клиентского лимита количества броней по телефону нет.

## Идемпотентность

Один ID — одна попытка. Повтор с тем же ресурсом, датой/временем и каноническими контактами возвращает тот же HTTP 201/результат без второй записи и события. Trim имён, регистр UUID и допустимые формы одного телефона не создают новую операцию. Повтор с другим валидным payload — 409 BOOKING_ID_CONFLICT. Некорректный payload сначала отклоняется валидацией.

Если ответ потерялся после COMMIT, повтор возвращает сохранённый результат. Это работает и после окончания аренды/выхода за текущее окно: повтор — не новая бронь. Если запись уже отменена, тот же payload получает **409 BOOKING_CANCELLED**, статус не меняется и событие не дублируется. Для самостоятельной новой записи нужен новый ID и допустимое свободное время. Старые строки 0001 без контактов не получают выдуманные данные: обычный POST не дополняет их, несовпадающий payload конфликтует.

Лимиты/Origin проверяются также для повторов. При 429/503 соблюдать Retry-After и ограниченное число повторов с прежним ID; не повторять бесконечно ошибки диска. Самостоятельных новых броней с разными ID может быть несколько.

## Ошибки

```json
{ "error": { "code": "BOOKING_OVERLAP", "message": "Выбранное время уже занято" } }
```

| HTTP | code | Значение |
|---|---|---|
| 400 | INVALID_JSON | Неверный JSON/UTF-8, дубли ключей или неплоский текстовый объект |
| 400 | INVALID_INPUT | Поля/типы/длины/UUID/параметры не соответствуют контракту |
| 400 | INVALID_DATE | Некорректная календарная дата; GET также проверяет окно |
| 400 | INVALID_TIME | Время не в формате HH:MM |
| 400 | INVALID_INTERVAL | Модель отвергла шаг/длительность/рабочие часы/прошлое или окно новой брони |
| 400 | INVALID_CONTACT | Общая проверка имени/фамилии/мобильного телефона не пройдена |
| 403 | ORIGIN_NOT_ALLOWED | Origin отсутствует/не совпадает или Sec-Fetch-Site не same-origin |
| 404 | RESOURCE_NOT_FOUND | Ресурс отсутствует |
| 409 | BOOKING_OVERLAP | Подтверждённый интервал уже занят |
| 409 | BOOKING_ID_CONFLICT | Тот же ID с другим payload |
| 409 | BOOKING_CANCELLED | Повтор ранее отменённой операции |
| 408 | REQUEST_TIMEOUT | Тело не прочитано за 5 секунд |
| 413 | BODY_TOO_LARGE | Тело больше 4096 байт |
| 415 | UNSUPPORTED_MEDIA_TYPE | Неподдерживаемый Content-Type/charset/сжатие |
| 429 | RATE_LIMITED | Исчерпан бюджет запросов; Retry-After в секундах |
| 503 | DATABASE_BUSY | Ограниченное ожидание writer-lock истекло; Retry-After: 1 |
| 503 | STORAGE_UNAVAILABLE | Файл/права/I/O/целостность/схема недоступны; Retry-After: 1 |
| 503 | API_UNAVAILABLE | Неверная конфигурация Origin/proxy identity; Retry-After: 1 |

Внутренние STORAGE_FAILURE/неожиданные исключения скрываются как STORAGE_UNAVAILABLE; native SQL, пути, стек и контакты не выводятся. Неисправное соединение закрывается. Непредусмотренные методы — стандартный Next 405, отсутствующие пути — Next 404 (вне JSON-контракта реализованных методов). `/api/health` сохраняет прежний `{status}` контракт.

## Минимальная защита от спама

В памяти **одного** процесса, отдельные 60-секундные окна:

| Метод | На identity | На весь процесс |
|---|---|---|
| GET availability | 60 | 600 |
| POST bookings | 10 | 60 |

Считаются и неуспешные допущенные запросы, включая повторы/неверный JSON. Проверка выполняется до чтения тела и БД. Телефон не используется. Map ограничена 1024 активными buckets, просроченные удаляются, активные для новых клиентов не вытесняются. Тело/контакты не хранятся в limiter; логов IP/контактов код не пишет. Retry-After ограничивает ожидание до нового окна.

По умолчанию `API_TRUST_PROXY=false`: Web Request не даёт надёжный peer IP, поэтому все клиенты имеют **общую identity shared**. Подмена X-Forwarded-For, Forwarded или X-Studio-Client-IP не даёт новый бюджет. Это безопасный локальный fallback, но за общим лимитом клиенты могут мешать друг другу.

`API_TRUST_PROXY=true` разрешает только одиночный валидный IP из **X-Studio-Client-IP**; отсутствующий/невалидный адрес даёт 503, не новый анонимный bucket. IPv6 канонизируется. X-Forwarded-For всё равно не используется. Это доверие к корректно настроенной инфраструктуре, а не автоматическая проверка peer со стороны Next.

Ограничения: после рестарта счётчики сбрасываются; несколько Node-процессов имели бы независимые бюджеты. Окна допускают всплеск на границе, NAT объединяет клиентов, ротация IP и боты с правдоподобными контактами полностью не исключены. Global budget ограничивает обход через много IP, но атакующий может исчерпать его и мешать клиентам. Origin защищает браузерный cross-site POST, **не аутентифицирует** curl/бота, способного поставить заголовок. Нет CAPTCHA/подтверждения телефона. Это минимальная защита для одного небольшого приложения, не полноценная защита от DDoS или ложных записей.

## Reverse proxy перед будущим публичным запуском

1. Задать точный `API_PUBLIC_ORIGIN=https://booking.example` (без пути/завершающего `/`/учётных данных). Не-HTTPS допустим только для loopback localhost/127.0.0.1/::1. По умолчанию — `http://127.0.0.1:3000`. Никакого вывода Origin из Host/X-Forwarded-Host/Proto.
2. Оставить Next на **127.0.0.1**, закрыть его порт извне и разрешить доступ только доверенному proxy. Только после этого включать `API_TRUST_PROXY=true`.
3. Proxy должен **перезаписывать**, не дополнять `X-Studio-Client-IP` проверенным адресом peer. При одном Nginx без CDN — `$remote_addr`; не `$http_x_forwarded_for`. Если позже появится ещё один proxy/CDN, сначала отдельно настроить точную цепочку доверия. Пример не решает её автоматически.
4. Ограничить размер/время приёма тела, подключения и частоту уже на proxy, включая health. Не писать тела/Origin с контактами/персональные данные в access/error-логи и аналитику. Не передавать контакты в URL.
5. HTTPS и сертификаты, общий connection/rate limit, мониторинг и внешние копии настраиваются отдельно при разрешённом VPS-этапе. Здесь ничего не развёрнуто.

Иллюстрация директив **для существующего HTTPS server/location**, не готовая конфигурация VPS:

```nginx
location /api/ {
    client_max_body_size 4k;
    client_body_timeout 5s;
    proxy_request_buffering on;
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host booking.example;
    proxy_set_header X-Studio-Client-IP $remote_addr;
    proxy_set_header X-Forwarded-For "";
    proxy_set_header X-Forwarded-Host "";
    proxy_set_header X-Forwarded-Proto "";
    proxy_set_header Forwarded "";
    proxy_connect_timeout 2s;
    proxy_read_timeout 10s;
    proxy_send_timeout 10s;
    proxy_no_cache 1;
    proxy_cache_bypass 1;
}
```

Не добавлять разрешающий `Access-Control-Allow-Origin: *`; API не выдаёт CORS grants. Origin браузера передаётся без подмены. Nginx client_body_timeout ограничивает паузы между чтениями, не полное время загрузки; нужны также общие ограничения подключений. Health не использует booking-limiter, чтобы диагностика не исчезала при его исчерпании; защищать его отдельно на proxy. Ни Origin, ни локальный limiter не заменяют эти настройки.

## Локальная проверка

Следовать [backend-local-setup.md](backend-local-setup.md) для `npm ci`, `db:env`, init/migrate/check. В `.env.sqlite.local` при необходимости добавить:

```dotenv
API_PUBLIC_ORIGIN=http://127.0.0.1:3000
API_TRUST_PROXY=false
```

Запустить `npm run dev:server` либо `npm run build:server` и `npm run start:server`. При другом порте поменять также Origin. Во втором терминале из checkout (только на локальной тестовой БД):

```bash
STUDIO_TEST_DATE=$(node --input-type=module -e 'import {addDays,moscowDate} from "./src/lib/availability.ts"; console.log(addDays(moscowDate(),1))')
curl -i "http://127.0.0.1:3000/api/availability?date=$STUDIO_TEST_DATE"
```

Для POST подставить эту дату в приведённый выше JSON, создать файл `/tmp/studio-test-request.json` с вымышленными контактами и новым UUID, затем:

```bash
curl -i http://127.0.0.1:3000/api/bookings \
  -H 'Origin: http://127.0.0.1:3000' \
  -H 'Content-Type: application/json' \
  --data-binary @/tmp/studio-test-request.json
```

Повтор команды с тем же файлом возвращает тот же результат. Новая заявка — новый UUID и свободный интервал. Не используйте реальные контакты. Не создавайте тесты на рабочей базе; публичная отмена отсутствует.

Воспроизводимая полная проверка без ручного редактирования БД:

```bash
npm test
npm run test:integration
npm run typecheck
npm run lint
npm run build:server
npm run test:api:http
npm run test:server:http
npm run test:server:http:failure
npm run build
npm run test:demo:isolation
```

API HTTP-тест создаёт собственную private temp SQLite, применяет миграции и запускает настоящий production Next на свободном **3012**. Использует вымышленные контакты, зарезервированные documentation IP и `https://studio.example` Origin. Trusted proxy имитируется явной конфигурацией/заголовком в тесте; настоящий Nginx/VPS не развёрнут и не проверен. Дополнительно запускается режим без доверия proxy. Все тестовые процессы/файлы завершаются/очищаются в finally. Старый health-тест использует 3011. Параллельно не пересобирать `.next-server`.

E2E: собрать static DEMO, запустить `npm run preview:demo`, затем `PLAYWRIGHT_BASE_URL=http://127.0.0.1:4173/loft-booking/ npm run test:e2e`. Проверки не требуют рабочей БД, внешних сервисов или Docker. Backend CI добавляет настоящий `test:api:http` и сохраняет все прежние проверки. Итоги и ссылка CI — в PR и [отчёте](booking-api-acceptance-v2.3.md).

## DEMO и границы

`route.server.ts` включён только SERVER-конфигурацией. Static DEMO не экспортирует `/api/`, SQLite/native-модуль, proxy-конфигурацию или серверные строки. Node DEMO также не регистрирует эти маршруты. Аудит экспорта проверяет новые маркеры API. Адрес https://jurist77.github.io/loft-booking/ и Pages workflow сохранены.

UI не обращается к API, не передаёт/сохраняет контакты и остаётся демонстрацией. В SERVER запись через UI пока отключена. Публичных операций отмены/изменения/списка/получения чужой брони по ID, авторизации, админ-панели, SMS/Telegram/оплаты нет. Этап 2.4 — только после приёмки и отдельного задания. До реальных контактов нужны согласованные правовые основания, уведомления/тексты и эксплуатационная защита; пример имени/телефона не является проверкой личности.
