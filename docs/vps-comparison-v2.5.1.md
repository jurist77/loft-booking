## Метод оценки ресурсов

1. Установить фактические лимиты VPS/виртуализации и размер файловой системы будущих `/opt`, `/var/lib`, `/var/backups`. Строки с одним устройством нельзя складывать. Контейнерные показатели хоста вместо VPS недопустимы.
2. Из нескольких типичных/загруженных периодов определить минимум MemAvailable, нагрузку CPU относительно vCPU, memory/io PSI, swap/OOM, загрузку VPN и свободный диск. `VmHWM` — максимум **одного процесса за его жизнь**, не суммарный одновременный пик VPN; WireGuard в ядре туда не входит. Сумма несинхронных VmHWM не является доказанным совместным пиком.
3. Для выбранного SERVER-артефакта на совпадающих Ubuntu/архитектуре/Node измерить RSS, VmHWM и cgroup MemoryPeak всего service при старте, обычном пятиэкранном пути, нескольких независимых клиентах, записи/восстановлении SQLite и корректном online backup. Сборку на VPS не выполнять. В этом этапе такого профиля приложения нет: **точные MB и MemoryMax не назначены**. Общие оценки Next.js не выдавать за измерение этого приложения. Профиль cloud будет только ориентиром до подтверждения на выбранном сервере в отдельно разрешённом этапе.
4. Бюджет RAM включает Node/native SQLite/cache, одновременную oneshot-задачу backup/шифрования, ОС/proxy/systemd, VPN и отдельный запас на наблюдаемые/неизвестные пики. Сравнить с минимальной доступной RAM в загруженные периоды, а не одним свободным снимком. Swap — аварийная поддержка, не штатная замена RAM. Не снижать FULL, WAL и надёжность ради прохождения бюджета.
5. Бюджет диска = распакованный новый и предыдущий релизы + артефакт при доставке + база/WAL с ростом + online snapshot/staging + журналы/cache + запас обновлений/восстановления. Измерить `du` этих **тестовых** объектов на builder, учесть peak распаковки, inode и дисковую задержку. В live VPN-каталоги для подсчёта не заходить. Full lock-based runtime-артефакт из проекта может быть существенно больше standalone; размер ещё не измерен.
6. Сеть: активные браузеры, static assets, API и offsite backup добавляют трафик. Неизвестный пик VPN/лимит канала провайдера — открытый риск. Backup назначать вне пика и ограничивать его пропускную способность после измерений. Короткий аудит не доказывает достаточный CPU/network headroom.

## Правила заключения

- **Подходит для тестового развёртывания:** измеренный профиль приложения/backup помещается с обоснованным запасом поверх VPN, нет давления/OOM, есть безопасный сетевой путь и проверяемый backup. Указать числа, периоды, остаточный запас и ограничения тестового трафика.
- **Подходит с ограничениями:** есть измеренный запас для явно ограниченного теста, но остаётся конкретная неопределённость (например, неизвестен недельный пик). Указать условия наблюдения и немедленной остановки сайта; не компенсировать нехватку RAM ненадёжными настройками SQLite или заведомо низким MemoryMax.
- **Не рекомендуется:** недостаточен запас RAM/диска/CPU, есть давление/OOM, сеть требует опасного вмешательства в VPN, либо нормальный профиль приложения не помещается. Рассмотреть Финляндию тем же методом; при непригодности обоих — остановиться, без покупки VPS.

Без фактов ни одну из трёх категорий серверам не присваивать. Если пики VPN неизвестны, это явно ограничивает достоверность любого будущего вывода. Выбор Финляндии предпочтительнее компромиссов с надёжностью сайта или вмешательства в шведский VPN.

Шаблон итогового решения: «Выбран ___, снимки ___, минимальная MemAvailable ___, измеренный service+backup peak ___, резерв ___, диск/иноды ___, HTTPS ___, VPN пики ___ (измерены/неизвестны), категория ___, условия остановки ___». Пока поля не заполнены — решения нет.
